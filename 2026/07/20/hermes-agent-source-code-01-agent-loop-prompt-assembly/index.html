很多Agent框架的介绍，会把核心原理压缩成一句话：

这句话没有错，但几乎没有工程价值。

真正把一个聊天模型变成Agent的，不是多写一个while，而是回答这些问题：

  • 系统提示词由哪些文件、配置和运行时信息拼出来？
  • 为什么记忆更新后，不应该立刻改写当前会话的Prompt？
  • 用户消息、外部记忆、插件上下文和MoA结果，哪些应该持久化，哪些只能临时注入？
  • 模型吐出半截工具参数时，系统为什么不能“猜一下”然后执行？
  • 多个工具调用如何并发，又如何避免文件写入冲突？
  • Agent所谓的“计划能力”，究竟来自独立Planner，还是模型与状态工具的组合？
  • 在崩溃、超时、中断或预算耗尽后，下一次会话如何知道之前发生了什么？

Hermes Agent把这些问题集中到了一个看似简单、实际边界极多的运行时里。

本文是“Hermes Agent源码解析”系列的第一章。分析锁定在Nous Research官方仓库commit：

仓库地址：NousResearch/hermes-agent。所有源码链接都固定到这个commit，避免后续重构让行号和结论漂移。

先给结论：真正的Loop已经不在run_agent.py

官方Developer Guide目前仍然把run_agent.py描述为“包含完整Agent Loop的大文件”。这在架构演进前是对的，但对当前源码已经不准确。

现在的真实调用链是：

run_agent.py里的AIAgent.run_conversation()仍然是公开入口，但它已经是一个薄转发器。它设置会话归因与辅助调用的ContextVar，然后把真正工作交给agent.conversation_loop.run_conversation()，最后在finally里恢复上下文。

源码入口：run_agent.py#L6079-L6127

这层转发器不是多余代码。它解决了两个实际问题：

  1. 保留稳定的公共入口，大量测试和外部调用不需要跟着内部拆分变化；
  2. 主模型、压缩、视觉、MoA和后台review等辅助LLM调用，可以继承同一个conversation root与usage归因。

真正约5600行的主循环，在agent/conversation_loop.py。这也说明一个事实：Agent Loop的复杂度不在循环语句，而在循环前后和每次迭代之间的状态处理。

一次用户请求，先经历一个“Turn序章”

在进入模型循环前，Hermes会调用build_turn_context()。

源码入口：agent/turn_context.py#L119-L623

这个函数原本是run_conversation()开头约470行的直线代码，后来被抽成独立模块。它只在每个用户turn开始时运行一次，负责建立本轮循环需要的固定上下文。

核心步骤可以压缩成九件事：

  1. 恢复上一个turn发生fallback前的primary runtime；
  2. 清空本轮重试状态，创建新的IterationBudget；
  3. 复制历史消息，避免修改调用方传入的列表；
  4. 把当前用户消息追加到历史；
  5. 从历史恢复TodoStore与周期性提示计数；
  6. 恢复或构建缓存系统提示词；
  7. 在调用模型前，立即把当前用户消息写入SessionDB；
  8. 检查是否需要预压缩上下文；
  9. 执行pre_llm_call插件，并预取外部记忆。

这里最值得学的，不是“准备数据”，而是两个持久化时机。

用户输入先写盘，再调用模型

turn_context.py会在Provider调用之前保存当前用户turn：

实际代码比这个简化片段多了锁、标记和异常处理，但设计目的很清楚：模型调用可能超时，进程可能被终止，Gateway也可能重启；只要用户消息已经进入系统，就不应该因为后续故障而凭空消失。

Todo不是临时UI，而是会话状态

如果历史存在、当前TodoStore还是空的，Hermes会调用_hydrate_todo_store(conversation_history)恢复任务列表。

这意味着Todo不是终端上画出来的装饰。它是可从持久会话恢复的执行状态。后面讲“计划能力”时，这一点很重要。

系统Prompt不是一层，而是三层冻结结构

Hermes的系统提示词由agent/system_prompt.py组装。

核心函数：build_system_prompt_parts()。

它明确把Prompt分成三层：

第一层：Stable——尽量永远不变的前缀

Stable层是Provider前缀缓存最希望复用的部分，主要包括：

  • SOUL.md身份；不存在时使用DEFAULT_AGENT_IDENTITY；
  • Hermes官方文档与hermes-agent Skill指引；
  • 任务必须完成、禁止伪造结果的通用约束；
  • 独立工具调用应批量发出的并行指导；
  • Memory、Session Search、Skills、Kanban等按工具可用性注入的行为指引；
  • Tool-use enforcement，以及GPT/Codex/Gemini等模型族的运行指导；
  • 可用Skills索引；
  • 执行环境、代码工作区、Python工具链、活跃Profile；
  • CLI、Telegram、Feishu等平台的输出提示。

这段设计有一个容易忽略的优点：只有真正加载了相关工具，才注入对应指导。

例如没有memory工具，就不需要把完整Memory工作流塞给模型；没有Skills工具，也不需要加载Skills索引。Prompt既是行为约束，也是运行时能力清单。

第二层：Context——本次运行环境的规则

Context层包含：

  1. 调用方传入的system_message；
  2. 当前项目的上下文文件。

项目文件不是全部叠加，而是按优先级选择：

这些文件会经过安全扫描、YAML frontmatter处理和动态长度限制。SOUL.md单独占据身份槽，因此成功加载后不会在Project Context里重复出现。

这正是Hermes能在不同仓库表现出不同工作方式的原因：模型不需要“记住”每个项目，项目规则在会话创建时进入Prompt。

第三层：Volatile——构建时会变化，但会话内仍被冻结

Volatile层包含：

  • MEMORY.md快照；
  • USER.md用户档案快照；
  • 外部记忆Provider提供的静态系统块；
  • 会话日期、Session ID、模型和Provider。

“Volatile”这个名字容易误导。它并不代表每次API调用都会重新生成。

build_system_prompt()最终把三层拼成一个字符串，缓存到agent._cached_system_prompt。继续会话时，Hermes还会尽量从SQLite恢复原始字节串。只要没有进入合法重建路径，这个字符串会在整个会话中原样复用。

所以更准确的理解是：

Stable、Context、Volatile描述的是“构建来源的稳定程度”；一旦会话Prompt构建完成，三者共同组成冻结前缀。

这就是为什么刚写入MEMORY.md的内容，不会马上改写当前会话的系统Prompt。否则每一次记忆更新都会让前缀缓存失效，也会让同一会话的身份和规则悄悄漂移。

为什么还要有API临时覆盖层？

缓存系统Prompt解决稳定性，但Agent每个turn又必须获得新信息。Hermes的解决办法不是修改缓存Prompt，而是在构造api_messages副本时注入临时内容。

源码入口：conversation_loop.py#L773-L1004。

每次循环都会：

  1. 修复损坏的工具参数和消息角色序列；
  2. 从持久messages复制出api_messages；
  3. 只在当前用户消息副本中加入外部记忆召回和插件上下文；
  4. 把缓存系统Prompt放在最前面；
  5. 追加ephemeral_system_prompt；
  6. 插入prefill消息和MoA上下文；
  7. 应用Provider缓存标记；
  8. 清理孤立Tool Result和thinking-only消息；
  9. 规范化空白与Tool JSON，提高Prefix/KV Cache命中率。

最关键的是第2步和第3步：

原始messages没有被修改。

因此，外部记忆和插件可以影响本次模型决策，却不会混入SessionDB，下一次恢复会话时也不会把一次临时召回误当成用户原话。

这是一条很值得复用的Agent设计原则：

持久历史记录“发生过什么”，API副本承载“这次调用还需要知道什么”。不要把两者混成同一个列表。

工具调用：先证明它完整，再允许它产生副作用

模型返回tool_calls后，Hermes不会立刻执行。

源码入口：conversation_loop.py#L4609-L5010。

它依次处理：

  1. 工具名修复与白名单校验；
  2. 参数JSON校验；
  3. 截断检测；
  4. delegate_task数量限制；
  5. 重复工具调用去重；
  6. 构建Assistant Tool Call消息；
  7. 写入SessionDB；

并发工具：不是全并行，而是分段执行

旧文档把规则简化为“单工具串行，多工具并行，交互工具例外”。当前实现已经更细。

调度器会把一批工具调用拆成连续Segment：

典型规则包括：

  • read_file、search_files、web_search等只读工具可以并行；
  • 文件操作只有目标路径不冲突时才能并行；
  • clarify永远是串行Barrier；
  • 普通Terminal、未知工具和参数无法解析的调用默认串行；
  • 并发Worker最多取调用数与8之间的较小值；
  • 工具可以乱序完成，但结果按模型原始Tool Call顺序回填。

这种设计比“全部并发”更接近真实工程：读多个文件应该一起做，但不能一边覆盖同一个文件，一边假设另一个Patch还在原始版本上运行。

Hermes有没有独立Planner？

第一眼看Hermes，会看到Todo、Plan Skill、Kanban、Delegation、Verification Gate，很容易以为主循环里藏着一个独立规划模型。

实际上，默认Agent Loop没有一个单独的“Planner LLM”。

计划能力来自四层组合：

1. 模型本身决定下一步动作

每轮模型根据当前消息和工具结果，选择继续调用工具还是输出最终文本。这是最基础的ReAct式控制。

2. Prompt要求复杂任务显式维护计划

系统Prompt会要求多步骤任务使用Todo、持续推进、完成后立即更新状态。这里提供的是行为约束，不是新的执行引擎。

3. TodoStore保存结构化状态

todo是Agent级工具。它维护pending / in_progress / completed / cancelled，并限制同一时刻只有一个任务处于in_progress。Turn开始时又能从历史恢复TodoStore。

这让“计划”从模型脑中的一段文字，变成可以检查和恢复的状态。

4. Kanban与Delegation扩展执行拓扑

Kanban把任务放入持久队列，由Worker领取；Delegation创建隔离子Agent，并给每个子Agent独立上下文和预算。它们改变的是任务拓扑和生命周期，不会替代主Agent对当前一步的决策。

所以更准确的结论是：

Hermes的计划能力不是“先让Planner写完计划，再让Executor照着跑”，而是模型决策、Prompt约束、Todo状态、任务队列和子Agent隔离共同形成的运行时能力。

这套方式的优点是灵活，缺点也明显：如果模型不维护Todo、不做验证，系统不会凭空获得一个完美计划。Agent的可靠性最终仍然取决于状态工具与证据门是否被正确使用。

Loop什么时候结束？

主循环并不是只看“有没有工具调用”。它可能因为以下原因离开：

  • 模型返回最终文本；
  • 用户中断；
  • Provider或Transport失败；
  • 工具Guardrail要求受控停止；
  • 上下文无法继续压缩；
  • 迭代预算耗尽；
  • 验证门保留了一个待确认的最终响应；
  • Codex等特殊模式走独立结束路径。

循环结束后，finalize_turn()统一收尾。

源码入口：agent/turn_finalizer.py#L30-L546。

它负责：

  • 预算耗尽时请求一次无工具总结，或保留验证门生成的响应；
  • 计算completed / partial / failed；
  • 保存Trajectory；
  • 清理VM与浏览器资源；
  • 修复中断后的Tool序列；
  • 写入最终Session快照；
  • 记录明确的turn exit reason；
  • 把未解决的文件修改失败追加到用户响应；
  • 触发输出转换、记忆复盘和Skill复盘。

这里又出现一条重要原则：清理、持久化或Trajectory写入失败，不应该吞掉已经生成的用户响应。finalize_turn()会独立捕获这些错误，把它们放进结果元数据，而不是让整个turn以空输出结束。

这套设计最值得学习的五点

1. Prompt稳定性是架构约束，不是省Token小技巧

为了保持字节级前缀稳定，Hermes把动态内容放进API副本，而不是不断重写系统Prompt和历史。这个选择影响了Memory、Plugin、Platform Hint和Compression的整个设计。

2. 持久化必须包围副作用

用户消息在模型前落盘，Assistant Tool Call在工具前落盘，最终结果在清理阶段再次落盘。可靠Agent需要的是事件顺序，不只是“定期保存”。

3. 对半截工具调用采取Fail-closed

文本回答可以容忍不完整，工具副作用不行。网络截断时拒绝执行，比聪明地修JSON更重要。

4. 并发必须识别冲突域

“工具可并发”不等于“这一批工具应该一起跑”。路径冲突、交互等待和未知副作用都必须成为Barrier。

5. 计划必须成为状态，完成必须有证据

Todo让计划可恢复，SessionDB让轨迹可恢复，Verification Gate和最终清理让“完成”不只是一句模型自述。

仍然存在的边界

Hermes的Loop很强，但不是魔法：

  • Prompt与工具Schema仍然可能占据大量Context；
  • 外部Provider对Tool Call、Reasoning和Cache-Control的实现并不一致；
  • 模型可能选择错误工具、重复调用或不维护Todo；
  • 并发路径判定依赖工具元数据，未知副作用只能保守串行；
  • Memory快照会话内冻结，提高了稳定性，但意味着新记忆通常要到重建后才进入系统Prompt；
  • 5600行主循环虽然已开始拆分，仍然是高耦合、高测试成本区域。

源码审计中，两组相关测试分别得到312 passed, 1 skipped与314 passed, 2 skipped，没有失败；两组存在覆盖重叠，不能简单相加。测试覆盖证明了很多局部契约，但不能替代真实Provider、Gateway和长会话压力下的运行验证。

  1. 先给结论：真正的Loop已经不在run_agent.py
  2. 一次用户请求，先经历一个“Turn序章”
    1. 用户输入先写盘，再调用模型
    2. Todo不是临时UI，而是会话状态
  3. 系统Prompt不是一层，而是三层冻结结构
    1. 第一层：Stable——尽量永远不变的前缀
    2. 第二层：Context——本次运行环境的规则
    3. 第三层：Volatile——构建时会变化，但会话内仍被冻结
  4. 一份真实Prompt，在API前是什么形状？
  5. 为什么还要有API临时覆盖层？
  6. 主循环：模型调用只是中间一步
  7. 工具调用：先证明它完整，再允许它产生副作用
    1. 半截JSON，宁可失败也不执行
    2. 工具副作用前，再做一次增量持久化
  8. 并发工具：不是全并行，而是分段执行
  9. Hermes有没有独立Planner？
    1. 1. 模型本身决定下一步动作
    2. 2. Prompt要求复杂任务显式维护计划
    3. 3. TodoStore保存结构化状态
