这些问题共同构成Hermes的Provider Runtime Resolution。

先给结论：Runtime Resolver是一台“策略编译器”

resolve_runtime_provider()最终返回一个Python字典，但把它理解成“读取配置并拼字典”会严重低估它。

更准确的模型是：

Hermes把用户意图、持久配置、环境凭证、OAuth状态、Credential Pool、Provider目录、模型名和安全策略，编译成一次可执行的Runtime Route。

它的主入口是：

  • resolve_runtime_provider()
  • resolve_provider()
  • resolve_provider_full()

解析完成后的典型结果是：

不同Provider还可能附带：

  • model
  • expires_at或last_refresh
  • region
  • guardrail_config
  • bedrock_anthropic
  • command与args
  • request_overrides
  • extra_headers
  • max_output_tokens

所以Runtime并不是“Provider配置”。它是本次Agent实例可以直接消费的路由快照。

真正调用链：先解凭证，再构造Agent

经典CLI路径从CLIAgentSetupMixin._ensure_runtime_credentials()开始：

源码位置：

  • _ensure_runtime_credentials()
  • _init_agent()
  • init_agent()

CLI不会只在进程启动时解析一次凭证。_ensure_runtime_credentials()明确会在使用Agent前重新解析，目的是拾取：

  • API key轮换；
  • OAuth token刷新；
  • Credential Pool当前选择；
  • /model之后的新Provider；
  • Base URL或API Mode变化。

如果api_key、base_url、provider、api_mode、ACP命令或实际模型发生变化，已有AIAgent会被丢弃并重新构造。原因很直接：OpenAI/Anthropic客户端在初始化时已经绑定了认证与路由，不能假装只改一个字符串就完成切换。

这也解释了为什么Runtime Route Signature包含：

Credential Pool对象没有进入签名，因为它可以在同一路由内部轮换凭证；Provider、协议或端点变化则必须重建客户端。

第一层解析：用户“请求了谁”

resolve_runtime_provider()开头先调用resolve_requested_provider()：

源码：runtime_provider.py#L541-L557

优先级非常明确：

这里有一个容易误读的细节：环境变量并不总比配置优先。

Hermes把通过hermes model保存的Provider选择视为正常运行的Source of Truth。这样，用户之前在Shell里残留的HERMES_INFERENCE_PROVIDER不会偷偷覆盖已经保存的端点。

进入auto以后，auth.py::resolve_provider()才进行更大的探测链：

  1. 显式API key或Base URL；
  2. config.yaml model.provider；
  3. OPENAI_API_KEY或OPENROUTER_API_KEY；
  4. OpenRouter Credential Pool；
  5. 其他Provider专属API key；
  6. auth.json active_provider中的OAuth登录；
  7. AWS Bedrock凭证链；
  8. 找不到则Fail Closed。

源码：auth.py#L1733-L1933

这个排序表达了一个重要原则：

明确的当前意图，应当压过陈旧但仍有效的登录状态。

例如用户曾登录Codex OAuth，但现在导出了DeepSeek key。Hermes会选择显式环境凭证，并写Warning说明它覆盖了旧OAuth Provider，而不是静默沿用旧登录。

第二层解析：Provider名字不是简单字符串

Hermes同时维护三类Provider事实：

  1. models.dev目录：Provider名称、Base URL、环境变量、模型元数据；
  2. Hermes Overlay：Transport、认证类型、Aggregator属性、额外环境变量；
  3. 用户配置：providers:和兼容的custom_providers:。

ProviderDef是三者合并后的统一结构：

源码：providers.py#L232-L244

这意味着Provider目录允许短暂陈旧，但不能因为目录服务不可用就让Hermes完全无法启动。

第三层解析：专用Provider先走短路

主函数并不是一条平均分配的流水线。部分Provider必须在通用逻辑之前短路：

  • moa返回本地虚拟Runtime；
  • Azure Anthropic直接进入anthropic_messages；
  • Azure Foundry读取端点、认证模式和模型族；
  • Vertex把凭证文件转换为短期OAuth token，不能把文件路径当API key；
  • Named Custom Provider先于通用Provider探测；
  • auto + 非已知云Base URL优先按Custom Endpoint处理，避免环境中的云Key把本地路由劫持走。

源码：runtime_provider.py#L1532-L1656

这类短路的共同原因不是“代码写乱了”，而是通用规则会破坏Provider自己的安全契约。

例如Vertex的GOOGLE_APPLICATION_CREDENTIALS是文件路径。如果它进入通用api_key解析器，系统可能把：

当成Bearer Token发送。这不仅会失败，还可能泄漏本机路径。

所以Resolver先调用get_vertex_config()生成短期Token，再把Token和计算出的Base URL交给OpenAI兼容客户端。

自定义端点看起来最简单：给一个URL和Key即可。实际上它是Provider解析里最敏感的一条路径。

API key不是随便“找一个能用的”

Hermes不会把OPENAI_API_KEY发送给任意OpenAI兼容端点。

更重要的是Host匹配不是字符串包含：

不会得到DEEPSEEK_API_KEY。Hermes取实际Hostname的可注册标签，Lookalike Host会导出ATTACKER_API_KEY，从而让真正的DeepSeek Key留在本机。

这段设计揭示了一个通用安全原则：

“协议兼容”不代表“认证域兼容”。Base URL、Provider身份和Credential Scope必须一起解析。

Credential Pool不是Key列表，而是有状态调度器

load_pool(provider)会把多个来源合并为CredentialPool：

  • 持久化Pool条目；
  • 单例OAuth/Auth Store；
  • 环境变量；
  • Custom Provider配置。

源码：credential_pool.py#L2491-L2554

Pool选择前会处理：

  • OAuth token是否接近过期；
  • 其他进程是否已经刷新Auth Store；
  • DEAD条目是否永久退出；
  • EXHAUSTED冷却是否到期；
  • 手动条目是否应该清理；
  • 环境来源缺失是否只是另一个进程没有同样环境，而不应删除全局条目。

支持的选择策略包括：

源码：credential_pool.py#L1459-L1638

遇到429或认证失败时，Pool不是简单index += 1。它会：

  1. 找到真正发出失败请求的Key；
  2. 根据状态码和错误上下文标记EXHAUSTED或DEAD；
  3. 写入冷却时间与失败原因；
  4. 重新选择下一条可用凭证；
  5. 对并发任务使用Soft Lease，尽量避免所有Worker抢同一Key。

源码：credential_pool.py#L1647-L1722

这意味着Credential Pool负责的是同一Provider内部的认证容错，而Fallback Provider负责的是跨Provider路由容错。两者不是同一层。

这里最值得复用的设计是：Provider是商业/认证身份，API Mode是协议身份。

两者必须分开建模。否则同一个Provider提供多种协议、同一个模型在不同Provider上受不同限制时，主循环会被大量例外污染。

Runtime进入AIAgent后，仍有一次防御性校正

CLI把Runtime字段原样传给AIAgent：

源码：cli_agent_setup_mixin.py#L342-L404

init_agent()仍会做防御性处理：

  • 无显式Provider时，可从Base URL识别Codex、xAI、Anthropic或Bedrock；
  • 验证Credential Pool是否与最终Provider和Base URL匹配；
  • 非Aggregator Provider会规范化模型名；
  • Direct OpenAI的新模型可升级到Responses；
  • Transport Cache会提前预热，尽早暴露缺失依赖或非法Mode。

这不是重复解析，而是不同信任边界：

  • Runtime Resolver负责从外部配置与凭证构造Route；
  • Agent Init负责验证构造后的Route是否满足Agent内部不变量。

Context Length是第二条解析链

resolve_runtime_provider()并不返回Context Length。

Context窗口在Agent初始化Context Engine时，通过get_model_context_length()单独解析：

源码：model_metadata.py#L2070-L2496

优先级远比“查一张模型表”复杂：

  1. model.context_length显式配置；
  2. Custom Provider的per-model配置；
  3. Endpoint-scoped元数据；
  4. 持久缓存，但会为Codex、Kimi、MiniMax、Grok等已知漂移主动失效；
  5. Bedrock静态表；
  6. Custom Endpoint /models或Ollama /api/show；
  7. 本地Server实时查询；
  8. Anthropic /v1/models；
  9. Copilot、Nous、Codex OAuth、GMI等Provider专用探测；
  10. OpenRouter实时元数据；
  11. models.dev目录；
  12. Hardcoded Family Defaults；
  13. 最终Fallback为256K。

为什么同一个模型名不能只对应一个数字？

例如同一Claude模型：

  • Anthropic原生API可能提供更大窗口；
  • Copilot返回账户实际可用的max_prompt_tokens；
  • Bedrock受AWS路径限制；
  • OpenRouter目录可能短暂低报；
  • 本地vLLM可能因为显存参数只开放32K。

所以缓存键和探测策略必须把Endpoint与Provider纳入考虑，而不是只用Model Slug。

初始化完成后，Hermes还会拒绝低于64K的Context窗口：

源码：agent_init.py#L1921-L1932

这是一条产品级约束：Hermes的Prompt、Tool Schema和多轮轨迹需要足够空间。一个模型“API可调用”，不代表它适合运行完整Agent Harness。

源码：cli_agent_setup_mixin.py#L49-L79

请求期间的Runtime Fallback

如果Agent已经创建，但Provider请求因重试耗尽、非重试错误或无效响应失败，Conversation Loop会激活下一条Fallback Route，交换Provider、Client、Base URL、API Mode和Credential Pool。

这部分属于第一章的Agent Loop，也是第三、四章Transport与Streaming会深入的内容。此处只强调边界：

Auth Fallback发生在Agent构造前；Runtime Fallback发生在Provider请求执行中。

Credential Pool轮换又位于两者之内：同一个Provider还有可用Key时，通常不应该立刻跳到下一个Provider。

官方文档与固定源码的差异

线上Provider Runtime Resolution给出了正确的高层模型，但部分实现描述已与源码漂移。

文档描述 0f102fa4d与当前main观察 判断
主实现包含_resolve_custom_runtime() 实际函数名是_resolve_named_custom_runtime() 符号名过时
providers/的get_provider_profile()是Runtime Resolver主数据源 固定commit和检查时的当前main，runtime_provider.py仍直接使用auth.py::PROVIDER_REGISTRY；hermes_cli/providers.py另行合并models.dev + overlay + user config 迁移目标已进入文档，但主路径尚未完全收敛
优先级是“显式→配置→环境→默认/auto” 高层正确，但真实代码还包含OAuth状态、Credential Pool、Host安全门、Provider专用短路和Auth Fallback 文档是概念简化
Fallback主循环位于run_agent.py 固定commit的真实主循环已拆到agent/conversation_loop.py 架构描述滞后
添加Provider Plugin即可无需Resolver分支 长期方向合理，但当前Resolver仍有Azure、Vertex、Bedrock、Codex、Nous等大量专用分支 “无需分支”尚不是完整现状

这不是说文档错误到不可用，而是说明：

文档描述的是稳定概念和目标架构；源码文章必须额外说明当前迁移阶段。

最值得复用的六条设计

1. 把用户意图和自动探测分开

显式选择、持久配置和auto探测不应该混成一个“第一个有值的环境变量”。只有这样才能解释路由，也能避免旧OAuth状态劫持当前选择。

2. Provider身份与Wire Protocol分开

一个Provider可以暴露多种协议，同一个协议也可以由多个Provider实现。把provider与api_mode拆开后，Agent Loop只依赖Transport契约。

3. Credential必须绑定Endpoint

Key不能因为“都是OpenAI兼容”就跨Host复用。准确Host匹配、Lookalike防护与Named Pool是Provider系统的安全底座。

4. Pool Rotation与Provider Fallback分层

先在同一认证域内轮换可用凭证，再决定是否切换Provider。否则一个临时429就可能把请求送到完全不同的价格、隐私和能力边界。

5. Model Metadata必须Provider-aware

模型名不是能力主键。Context Length、输出上限、Vision和Reasoning能力都可能由Endpoint、账户与协议共同决定。

6. Resolver输出应当可审计但不能泄密

source、requested_provider、api_mode和Route Signature让行为可解释；api_key与extra_headers则必须留在内存，不能进入普通日志和会话持久化。

仍然存在的边界

Provider Runtime Resolution很强，但仍有明显成本：

  • runtime_provider.py超过2000行，Provider专用分支仍然很多；
  • auth.py、runtime_provider.py、providers.py与新providers/插件注册表之间存在迁移期重叠；
  • Alias在多个模块保留兼容逻辑，长期可能漂移；
  • URL启发式只能识别约定，不能真正证明远端支持某协议；
  • models.dev、Provider /models和Hardcoded Defaults之间可能互相矛盾；
  • no-key-required是适配OpenAI SDK的占位值，不代表远端真的无需认证；
  • Fallback可能改变成本、数据边界和模型能力，配置者必须明确接受这种变化；
  • 实际OAuth刷新、429冷却和Provider故障仍需真实环境压力验证。
