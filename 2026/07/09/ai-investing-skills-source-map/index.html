别急着让 AI 炒股：这 16 个开源项目，真正值钱的是三层底座

这张「AI 投资 Skills 大全」看起来像一份工具清单，但如果只按 star 排名去装项目，大概率会走偏。

真正值得看的，不是「哪个项目最像 AI 炒股神器」，而是它们背后正在分化出的三层基础设施：数据底座、研究/回测引擎、Agent 决策层。

换句话说，AI 金融开源圈已经不是简单地「把 ChatGPT 接到股票数据上」。一部分项目在补金融数据的管道，一部分在补量化研究和交易执行的工程底座，还有一部分在尝试让多个 Agent 像投研团队一样辩论、归因、风控、下结论。

但这里也有一个必须先说清楚的判断：越接近“自动交易”的项目，越不能只看 demo，必须看风控、数据契约、回测边界和免责声明。

本文把图里的 16 个项目逐一找到了源码出处，并 clone 了其中 8 个更重要、更有代表性的仓库做源码级拆解。结论先放前面：

  • 最值得做底座研究：OpenBB、Qlib、Lean、vn.py、MarS；
  • 最值得看 Agent 架构：TradingAgents、ai-hedge-fund、FinRobot；
  • 最适合个人自动化提醒/盯盘：daily_stock_analysis、go-stock；
  • 最需要警惕营销味和实盘误用：所有强调自动执行、模型交易、收益展示的项目。

这张表里有几个细节值得注意。

第一，原图里的热度并不总是最新。例如 TradingAgents 已经冲到 9 万 star 以上，明显超过原图里写的 9.3K；MarS 也不再是约 1K，而是 1.7K+。这类图适合做线索，不适合当最终事实源。

第二，OpenBB 的 GitHub API license 字段显示为 NOASSERTION，但项目页和 README 摘要显示为 AGPLv3；FinceptTerminal 也类似，README 徽章显示 AGPL-3.0。也就是说，license 不能只信 GitHub API 一个字段，真正要商用集成必须回到仓库 LICENSE 文件。

第三，很多项目把「AI 投资」写得很热闹，但真正工程含量分布并不均匀：有的是完整交易引擎，有的是数据连接器，有的是 notebooks，有的是 prompt/skill 框架。

二、8 个源码深挖项目：为什么选它们

我没有把 16 个项目平均拆开，因为那样只会变成 README 摘要。更合理的做法，是挑 8 个有代表性的源码下钻：

三、TradingAgents：最像“投研公司组织结构”的多 Agent 框架

源码位置：TauricResearch/TradingAgents

TradingAgents 的核心不在「调用一个 LLM 给买卖建议」，而在它把投资决策拆成了一个比较完整的组织结构：

源码里最关键的是 tradingagents/graph/setup.py。它用 LangGraph 的 StateGraph 把上述角色接成有条件跳转的工作流：

  • 分析师节点先调用工具拿数据；
  • 工具节点返回后回到分析师；
  • 清理消息后进入下一个分析师；
  • 多个分析师完成后，进入牛/熊研究员辩论；
  • Research Manager 汇总投资计划；
  • Trader 生成交易计划；
  • 最后进入三类风险分析师和 Portfolio Manager。

有意思的是，项目还专门处理了一个多 Agent 系统的真实工程问题：图路由漂移。

在 setup.py 里，DEBATE_PATH_MAP 和 RISK_ANALYSIS_PATH_MAP 把所有可能路由目标都列出来，避免 prompt/i18n/标签改动后，LangGraph 因为找不到 path map 中的节点而中途崩掉。这不是花哨功能，而是多 Agent 编排真正会遇到的稳定性问题。

另一个值得看的文件是 tradingagents/graph/trading_graph.py。这里做了几件比较工程化的事：

  • 把 deep_thinking_llm 和 quick_thinking_llm 分开；
  • 根据 provider 适配 Google thinking level、OpenAI reasoning effort、Anthropic effort；
  • 用 ToolNode 统一市场、新闻、fundamental、prediction markets 等工具；
  • 引入 checkpoint / resume；
  • 用 TradingMemoryLog 做结果记录和后续反思。

我的判断：TradingAgents 的价值不在它能不能今天帮你赚钱，而在它展示了金融 Agent 系统如何从“单 prompt”变成“可编排组织”。

但它也有明显边界：Agent 越多，幻觉、数据延迟、工具失败和成本都会被放大。项目虽然做了 verified market snapshot、checkpoint、vendor fallback 等增强，但实际用于交易仍然必须有独立风控和回测验证。

四、OpenBB：AI 金融应用最缺的不是模型，而是数据入口

源码位置：OpenBB-finance/OpenBB

OpenBB 是这批项目里最像「基础设施」的一个。

README 对它的定位是 Open Data Platform：连接一次，多处消费。Python、REST API、Workspace、Excel、MCP server、AI copilot 都可以从这个数据层取数据。

源码里值得看的不是某个指标函数，而是它的抽象边界。

openbb_platform/core/openbb_core/app/router.py 定义了 OpenBB 自己的 Router：它把一个普通函数包装成 API route，同时塞入：

  • response model；
  • provider examples；
  • openapi_extra；
  • mcp_config；
  • widget config。

这意味着 OpenBB 不是简单封装一堆金融 API，而是在把金融数据函数同时暴露给 API、UI、Agent/MCP 等多个消费端。

另一个关键抽象在 provider/abstract/fetcher.py：

这是非常经典也非常稳的 TET 结构：

  1. 先把标准参数转成 provider-specific query；
  2. 再去具体数据源抓取；
  3. 最后转换成统一的 OpenBB 数据模型。

这层价值很大：如果没有统一数据模型，Agent 调 10 个金融数据源只会得到 10 种字段、10 种异常、10 种时间口径。

所以 OpenBB 更像「金融 Agent 的数据插座」。你可以不用它的 Workspace，但它的数据抽象和 provider 插件系统值得研究。

风险也很清楚：金融数据源的许可、延迟、字段口径、商业使用权都很复杂。OpenBB 能统一入口，不等于替你解决数据合规。

五、Qlib：量化研究真正需要的是“从数据到回测”的闭环

源码位置：microsoft/qlib

Qlib 是微软开源的 AI-oriented quantitative investment platform，覆盖数据处理、模型训练、回测、组合优化、执行和在线服务。

源码结构很清晰：

我重点看了 qlib/backtest/executor.py。它的 BaseExecutor 不是简单地「把订单按价格成交」，而是维护了一套交易执行所需的公共基础设施：

  • trade_calendar：交易日历和步进；
  • trade_account：账户与持仓；
  • trade_exchange：市场/交易所抽象；
  • indicator_config：成交质量指标，如 price advantage、fulfill rate；
  • track_data：为 RL agent 收集执行轨迹。

里面有一段注释很说明问题：collect_data 被设计成 generator，因为它既要推进交易，又要为嵌套 executor / RL 训练收集中间状态。

这就是 Qlib 和很多「LLM 给建议」项目的差别：Qlib 关心的是投资研究如何被复现、回测、记录和生产化，而不是今天模型说买还是卖。

Qlib 的另一个新信号是它正在和 RD-Agent 结合，把自动因子挖掘、模型优化接到量化研发流程中。这比单纯让 LLM 读新闻更接近专业投研里的“研发自动化”。

六、ai-hedge-fund：概念很直观，但它自己也强调不是实盘系统

源码位置：virattt/ai-hedge-fund

这个项目很好理解：把一群著名投资人/投资风格做成 Agent，比如 Graham、Buffett、Munger、Peter Lynch、Damodaran、Burry、Cathie Wood 等，让它们分别分析，再由 risk manager 和 portfolio manager 做最终决策。

src/main.py 里核心工作流很短：

它用 LangGraph 的 StateGraph 串起来。和 TradingAgents 相比，ai-hedge-fund 的图更直接、更适合教学和 PoC。

真正值得看的是两个约束模块。

src/agents/risk_manager.py 不让 LLM 直接拍脑袋定仓位，而是先用确定性代码算：

  • 当前价格；
  • 日波动率、年化波动率；
  • 波动率分位数；
  • 多标的相关性；
  • 组合总价值；
  • 剩余仓位上限。

src/agents/portfolio_manager.py 又进一步把允许动作算出来：

  • buy 最多可以买多少；
  • sell 最多能卖已有多头；
  • short 受保证金和仓位限制；
  • cover 只能覆盖已有空头；
  • 没有合法交易时直接预填 hold，不发给 LLM。

这是非常重要的工程原则：让 LLM 做判断，但不要让 LLM 越过确定性风控边界。

不过项目 README 也写得很明确：这是 proof of concept，教育和研究用途，不是实盘交易或投资建议。这句话不能忽略。

七、daily_stock_analysis：个人盯盘/推送系统，工程量比想象中大

源码位置：ZhuLinsen/daily_stock_analysis

这个项目在中文圈很容易火，因为它击中了一个具体需求：每天对自选股做 AI 分析，然后自动推送。

但源码不是一个小脚本，而是一个完整应用：

src/core/pipeline.py 非常长，超过 3000 行，职责包括：

  • 数据抓取；
  • 技术分析；
  • 新闻搜索；
  • LLM 分析；
  • 诊断记录；
  • 决策信号提取；
  • 通知发送；
  • 交易时段判断；
  • 多市场代码标准化。

它的优点是功能非常完整，适合真实个人使用场景；缺点也来自这里：主 pipeline 过重，长期维护容易变成“所有东西都往一个调度器里塞”。

更有意思的是 src/agent/orchestrator.py。项目把 Agent 模式分成：

  • quick：Technical → Decision；
  • standard：Technical → Intel → Decision；
  • full：Technical → Intel → Risk → Decision；
  • specialist：Technical → Intel → Risk → Specialist → Decision。

它还处理了全局 timeout、子 Agent timeout、预算不足自动降级、dashboard partial 标记等细节。

这类项目最适合“人监督的自动化盯盘”，不适合直接理解成“AI 自动炒股”。

八、FinGPT 与 FinRobot：一个偏模型，一个偏 Agent 工作流

源码位置：AI4Finance-Foundation/FinGPT、AI4Finance-Foundation/FinRobot

FinGPT 是金融大模型方向的代表。源码里有 FinGPT Forecaster、Benchmark、RAG、Sentiment Analysis 等目录。

它更像「金融 LLM 数据与微调实验室」，重点不是交易执行，而是金融文本、新闻、基本面如何进入 LLM 训练/推理流程。

FinRobot 则更偏 Agent 平台。finrobot/agents/workflow.py 基于 AutoGen，定义了 FinRobot(AssistantAgent)，再往上封装：

  • SingleAssistant；
  • SingleAssistantRAG；
  • Shadow Agent；
  • GroupChat / GroupChatManager。

它把 agent profile、toolkits、proxy、RAG function 组合起来，更适合自动生成研报、跑工具链、做多角色分析。

一句话区分：FinGPT 解决“金融模型和数据集怎么来”，FinRobot 解决“金融分析任务怎么被 Agent 执行”。

九、MarS：最硬核，但当前不要误读成完整可复现产品

源码位置：microsoft/MarS

MarS 的方向和前面项目完全不同。它不是让 LLM 读新闻，也不是做股票仪表盘，而是要做金融市场的 generative foundation model。

项目论文叫 MarS: a Financial Market Simulation Engine Powered by Generative Foundation Model，核心是 Large Market Model：在订单事件级别生成市场行为。

源码里有两层：

mlib/core/engine.py 是事件驱动模拟器，用 heap queue 管理事件：

  • MarketOpenEvent；
  • AgentStatesUpdateAndWakeup；
  • ExchangeReceiveOrdersEvent；
  • AgentReceiveTradingResultEvent；
  • MarketCloseEvent。

它的核心循环就是不断 pop event，然后按事件类型更新 agent、exchange、order owner、transaction。

market_simulation/models/order_model.py 更有意思。它定义 OrderTokenizer，把订单事件离散化为 token，包括：

  • order type；
  • price level；
  • predicted order volume；
  • order interval；
  • change to open；
  • time to open；
  • LOB snapshot。

然后用 LlamaForCausalLM 作为 decoder 来预测下一个订单 token。

这是一个非常硬核的方向：把金融市场当成一个可生成的“世界模型”。

但当前仓库也有明显限制：README 写明核心代码和工具已发布，关联 Hugging Face 模型还在 final review，部分 demo 完整功能依赖模型发布。因此它更适合研究“金融世界模型怎么建”，不适合马上拿来做完整仿真产品。

十、剩下 8 个项目怎么定位

不是没价值，只是优先级不同。

  • vn.py：国内量化交易框架老牌项目，交易接口、CTA、回测、实盘生态成熟。它不靠 AI 噱头，价值在交易工程经验。
  • FinceptTerminal：定位个人 Bloomberg 替代品，C++/Qt 终端形态很有野心；但 README 已提示 2026 年 6 月后公开版改为月更、私有版优先，维护节奏要注意。
  • backtrader：轻量回测框架经典项目，适合教学和策略原型；但主仓库更新频率较低，现代化程度不如新项目。
  • Lean：QuantConnect 的专业级算法交易引擎，C# / Python、回测/实盘/另类数据生态强，是工程成熟度很高的交易底座。
  • Vibe-Trading：偏个人 trading agent 平台，结合 FastAPI、React、MCP、多 Agent；很新，适合观察“零代码交易 Agent”叙事。
  • nofx：Go + React 的 AI trading terminal，强调 US stocks、commodities、forex、crypto 和交易执行；AGPL-3.0，接近实盘链路，风险边界要看得更严。
  • ai-berkshire：价值投资 skill/框架，中文语境很强，适合研究“方法论结构化”；但投资收益展示类内容必须谨慎看待，不能当作未来收益证明。
  • go-stock：本地隐私导向的 AI 股票分析工具，支持多模型、本地数据保留，适合普通用户盯盘。

十一、如果你真的要学习源码，推荐顺序是这样

不要按 star 读，按工程层级读。

第一层：数据与接口

先看 OpenBB、vn.py、Lean。理解真实金融系统里最麻烦的问题：数据源、字段口径、交易日历、行情延迟、broker/exchange adapter。

第二层：研究与回测

再看 Qlib、backtrader、Lean。重点看 dataset、model、strategy、executor、account、exchange、position，而不是急着接 LLM。

第三层：Agent 决策

最后看 TradingAgents、ai-hedge-fund、FinRobot、daily_stock_analysis。重点看：

  • Agent graph 怎么编排；
  • 工具调用失败怎么降级；
  • LLM 输出如何结构化；
  • 哪些约束由代码确定，哪些交给模型判断；
  • 有没有 checkpoint、memory、risk guardrail。

第四层：市场仿真 / 世界模型

有余力再读 MarS。它不是最容易用的，但概念最深：订单事件级市场模拟，比“预测明天涨跌”更接近金融系统建模本质。

十二、最后的判断：AI 投资项目的分水岭来了

这 16 个项目可以分成两类。

一类在认真补底座：数据、回测、撮合、风控、模拟、实验记录。这类项目短期不一定性感，但长期价值更稳。

另一类在包装体验：多 Agent、自动研报、自然语言下单、聊天式策略生成。这类项目传播快，但真正能不能用，要看它是否把模型关在确定性边界里。

判断一个 AI 投资项目，不要问它“能不能预测上涨”。要问四个问题：

  1. 数据从哪里来，字段和时间口径是否可信？
  2. 回测有没有防 look-ahead bias？
  3. 风控是否由确定性代码约束，而不是让 LLM 自己承诺？
  4. 输出是否能被记录、复现、审计和复盘？

能回答这四个问题的项目，才值得深读源码。

否则 star 再高，也只是把金融市场包装成了一个更漂亮的聊天窗口。
