Pi Coding Agent 71K Star 背后：核心不是 Prompt，而是两层 Loop

Nathan

很多 Coding Agent 喜欢把自己讲成一套复杂的“自治系统”：规划、反思、多 Agent、长期记忆，名词一个比一个大。

Pi 走了另一条路。

这个已经拿到超过 7.1 万 Star 的项目，把最关键的 Agent Loop 写成了两个 while。没有工作流图，没有任务 DAG，也没有藏在框架深处的 Planner。模型回答、工具执行、结果回填；只要模型还在调用工具，循环就继续。

看起来简单得近乎寒酸。

但真正读完源码会发现，Pi 的功夫不在于把 Loop 写复杂，而在于把模型流、工具副作用、事件顺序、用户插话和会话恢复之间那些最容易出错的边界处理清楚。

本文基于 earendil-works/pi 的 main 分支 commit 97f9978fa66685f78d2da19ae22e20c46d125f74。这是原 badlogic/pi-mono 迁移后的官方仓库；分析对应 npm 包版本 0.80.7。

先说结论：Pi 不是“会规划的 Agent”，而是一个 Agent Harness

Pi 的 README 把自己称为 Agent Harness，这个词比“智能体框架”准确得多。

Harness 原本是“线束”或“安全带”：它本身不负责思考，而是把几个会活动、会失败的部件可靠地绑在一起。Pi 绑住的是四层东西：

  • pi-ai：把 Anthropic、OpenAI、Google 等不同 Provider 统一成同一种消息和流式事件。
  • pi-agent-core：负责模型调用、工具执行、消息队列和生命周期事件。
  • AgentSession：补上持久化、扩展、重试、上下文压缩和动态工具集。
  • pi-coding-agent：提供 CLI、TUI、RPC、SDK，以及 read、bash、edit、write 等真正面向开发者的工具。

完整调用链可以压缩成一行：

这一区分非常重要。pi-agent-core 不是完整 Coding Agent，它甚至不负责把聊天记录写到磁盘。它只是一台内存里的“消息—工具循环发动机”。真正让 Pi 能恢复会话、切换模型、装 Skill 和扩展的，是上面的 AgentSession。

Pi 的设计选择很克制：把必须稳定的内核做小，把产品能力留在外层组合。

两层 while，分别解决两类“继续”

核心代码在 packages/agent/src/agent-loop.ts。runLoop() 从第 155 行开始，主体只有约 120 行。

它不是一个循环，而是两个套在一起的循环：

内层循环：模型还要不要继续调用工具

内层循环的条件是：

一次循环就是一个 turn：

  1. 把待处理的 Steering 消息放进上下文；
  2. 调用模型并流式接收 Assistant Message；
  3. 找出其中所有 Tool Call；
  4. 执行工具，把 Tool Result 写回上下文；
  5. 发出 turn_end；
  6. 如果模型刚才调用了工具，再让模型看一次工具结果。

这就是 Coding Agent 最基本的呼吸节奏：

Pi 没有在模型外再造一个任务规划器。所谓“规划”，本质上仍是模型通过连续 Tool Call 表达出来的。

外层循环：这轮结束后，用户还有没有排队任务

当模型不再调用工具、Steering 队列也空了，内层循环准备结束。此时外层循环再检查 Follow-up 队列。

  • 有 Follow-up：把它变成新的 Pending Message，再跑一轮。
  • 没有 Follow-up：发出 agent_end，整个 run 结束。

所以 Pi 里有两种“用户插话”：

  • Steering：当前 turn 的工具全部执行完后、下一次模型调用前插入，用来改变正在进行的任务。
  • Follow-up：等 Agent 本来要停下时再开始，适合“做完以后再帮我总结”。

这个语义比许多聊天式 Agent 清楚。它不假装能在任意一条 shell 命令执行到一半时瞬间改变方向；Steering 只在安全的 turn 边界生效。

这也意味着一个限制：Steering 不是抢占式中断。 如果当前工具批次里有一个执行十分钟的命令，用户的新指令必须等这批工具结束，除非显式触发 Abort。

Streaming 不是打印字符，而是维护一条“活消息”

streamAssistantResponse() 做了一件很实用的事：模型开始输出时，Pi 先把 Partial Assistant Message 放进当前 Context；随后每个 text_delta、thinking_delta、toolcall_delta 到来，都用新的 partial message 替换最后一条消息。

最终收到 done 或 error 后，再把它替换成 Final Message。

这让 TUI、日志、扩展和状态读取者看到的是同一个逐渐长大的 Assistant Message，而不是一堆互相独立的 token 片段。

围绕这条消息，Pi 发出一组稳定事件：

低层 agentLoop() 返回的是观察型 EventStream；消费者处理事件并不会阻塞生产者。高层 Agent 则把 processEvents() 直接交给 Loop 并逐个 await，因此事件监听、状态归约和持久化可以成为真正的顺序屏障。

这不是一个显眼的功能，却是 UI 不乱、消息不丢的关键。

Agent.waitForIdle() 甚至会等 agent_end 的异步监听器全部完成才返回。换句话说，agent_end 代表“不会再产生新事件”，而 Idle 代表“连收尾工作也已经落盘”。

工具默认并行，但 Transcript 绝不能乱

Pi 当前默认并行执行同一条 Assistant Message 中的多个 Tool Call。

但它没有简单地 Promise.all(tool.execute)。整个批次被拆成三段：

  1. Prepare：兼容旧参数格式；
  2. Validate / Before Hook：按 Schema 校验，并让扩展决定是否阻止；
  3. Execute / After Hook：并行执行，再允许扩展改写结果。

真正聪明的是结果排序：

假设模型依次发出 A、B、C 三个工具，实际完成顺序是 B、C、A：

  • tool_execution_end 按 B、C、A 实时发出，UI 可以立刻更新；
  • 写入 Transcript 的 Tool Result 仍按 A、B、C 排列，保证和模型原始 Tool Call 一一对应。

Pi 把“观测的实时性”和“历史的确定性”分开了。

还有两个安全细节值得抄作业：

  • 如果一个批次里任何工具声明 executionMode: "sequential"，整批工具都会串行执行，避免写文件等副作用互相踩踏。
  • 如果模型因为输出 token 上限而以 stopReason: "length" 结束，Pi 不执行其中任何 Tool Call。因为被截断的 JSON 有时仍能被“抢救”为合法参数，但内容可能已经悄悄缺了一半。

Coding Agent 在这层“整批开关”之外，又给 edit 和 write 加了一把更细的锁。withFileMutationQueue() 用文件真实路径做 Key：同一个文件的修改严格排队，不同文件仍然并行。即使 Abort 已经到达，它也会等当前文件系统操作真正结束后再释放锁，避免“调用方以为取消了，旧写入却稍后落盘”这种幽灵覆盖。

第二条尤其重要。许多 Agent 只验证“JSON 能不能解析”，Pi 进一步问了一句：“这份 JSON 是不是在完整响应里产生的？”

这不是为了显得谨慎而加的理论防线。2026 年 7 月 7 日，项目在 commit 351efc82 中专门修复了 issue #6284：流式 JSON 的容错解析可能把半截参数补成一个“合法但不完整”的对象。最终方案不是继续改 Parser，而是在 Agent Loop 里拒绝执行整个截断批次，让模型重新发出完整调用。

AgentMessage：把 UI 历史和模型上下文分开

Pi 内部使用的不是普通 Message[]，而是可扩展的 AgentMessage[]。

它可以包含：

  • 标准 user / assistant / toolResult；
  • 扩展产生的 custom message；
  • 只给 UI 看、不该发给模型的状态消息；
  • 压缩摘要和分支摘要。

每次真正请求模型之前，消息经过两道门：

transformContext() 适合做裁剪、压缩和外部上下文注入；convertToLlm() 则负责过滤 UI-only 消息，把自定义类型翻译成模型认识的 user / assistant / toolResult。

这个抽象解决了一个常见错误：很多 Agent 把“界面上显示过的东西”直接等同于“下一轮全部发给模型的东西”。结果日志、提示条、插件状态甚至不可见元数据都可能污染 Prompt。

Pi 明确承认：会话历史是一套产品数据，模型上下文只是它在某个时刻的投影。

真正的长期状态，是一棵 JSONL 树

pi-agent-core 的 Agent 只保存内存数组。Coding Agent 的 SessionManager 才负责持久化。

Pi 的会话文件是 append-only JSONL：每行一个 Entry。除了消息，还会记录模型切换、Thinking Level、Compaction、Branch Summary、Label 和扩展自定义状态。

因此它不是一条只能向前的聊天日志，而是一棵树。/fork 不需要复制并修改原历史，只需选择新的叶子；恢复上下文时，从当前 Leaf 沿 parentId 回到 Root，再反转成一条分支。

Context Compaction 也不是暴力删除旧消息。Pi 会追加一条 Compaction Entry，记录摘要、保留起点和压缩前 token 数；构建模型上下文时，再把被摘要覆盖的旧节点排除。

这让“完整审计历史”和“送进模型的精简上下文”能够同时存在。

Coding Agent 在核心 Loop 外又套了一层恢复循环

AgentSession._runAgentPrompt() 还有一个很短的循环：

它负责的不是工具链，而是运行后恢复：

  • Provider 临时错误是否自动重试；
  • Context Overflow 是否先压缩再续跑；
  • 扩展是否在 agent_end 时又排进了新消息；
  • 队列里是否还有工作。

这说明 Pi 实际上有三种不同尺度的循环：

  1. Tool Loop：模型—工具—模型；
  2. Follow-up Loop：一个任务结束后处理排队任务；
  3. Recovery Loop：一次 run 结束后重试、压缩或继续。

把它们分开，比在一个巨型状态机里塞满所有分支更容易测试。

Overflow 恢复也有限制：Pi 最多做一次“压缩后重试”。如果仍溢出，就停止并提示换更大上下文模型或减少输入，避免无休止地烧 token。

扩展很强，但它也是信任边界

Coding Agent 把 Extension Hook 接到了 Provider 请求、Context、Tool Call、Tool Result、Compaction 和 Session 生命周期上。

beforeToolCall 可以阻止工具执行，afterToolCall 可以替换结果；每个新 turn 开始前，系统还会重新读取当前模型、Thinking Level、工具列表和 System Prompt，所以扩展可以在运行中改变下一轮能力。

但不要把 Hook 误解成沙箱。

项目 README 明确写着：Pi 默认没有限制文件系统、进程、网络或凭据访问的内建 Permission System。它以启动进程的用户权限运行。需要更强边界时，应放进 Docker、micro-VM 或策略沙箱。

Pi 的 Project Trust 也只是“是否加载项目本地设置、扩展、Skill 和 Prompt”的启动门禁。拒绝 Trust 能阻止仓库在启动前悄悄注入本地扩展，却不能限制模型启动后要求 Bash、Read 或 Write 做什么，更不能消除仓库文档和构建输出里的 Prompt Injection。

源码还暴露出一个更细的边界：Tool Arguments 先做 Schema 校验，再交给 beforeToolCall。Hook 拿到的是同一个可变参数对象；测试甚至明确证明，Hook 修改参数后不会再次校验。

这给兼容和拦截带来灵活性，但也意味着：

扩展不是“不可信插件”，而是 Agent Runtime 的受信代码。

如果未来要做企业级插件市场，这里需要不可变参数、Hook 后重校验，或者更明确的进程隔离。

它做得好的地方，以及没做的地方

Pi 最值得借鉴的不是“代码短”，而是几个边界选择：

  1. 把 Agent 内核限制在消息和工具循环。 持久化、压缩、重试都在外层。
  2. 事件和状态有清晰的完成语义。 agent_end 与 Idle 不混为一谈。
  3. 并行执行不牺牲历史确定性。 完成事件按实时顺序，Transcript 按源顺序。
  4. 上下文是会话的投影。 产品消息不必全部污染模型输入。
  5. 对截断 Tool Call 默认不信任。 宁可让模型重发，也不执行半截参数。

它同样有明确边界：

  • 没有显式 Planner、Task Graph 或可证明的任务完成标准；
  • Steering 要等当前工具批次结束，不是实时抢占；
  • 一个 sequential 工具会让整批串行，锁粒度偏粗；
  • Low-level Hook 的“不抛异常”主要依赖调用方契约，不是完全隔离；
  • 核心 Agent 没有持久化，直接使用 pi-agent-core 的应用必须自己补状态层；
  • 默认没有权限沙箱，Hook 只能做策略拦截，不能代替系统隔离。

所以 Pi 不是一个“自主性最强”的 Agent。它更像一台透明、可拆、方便嵌入的发动机。

最后的判断

复杂 Agent 框架常犯一个错误：把所有可靠性问题都包装成“让模型再想一次”。

Pi 的源码给出了相反答案。模型负责决定下一步，Runtime 负责保证下一步不会因为乱序、半截 JSON、丢失事件或不可恢复的历史而失控。

Agent 的上限由模型决定，但 Agent 能不能长期工作，取决于 Loop 如何对待边界。

Pi 没有给循环加更多魔法。它只是把每一次继续、停止、插话、并发和恢复，都变成了可以读懂、可以测试的代码。
