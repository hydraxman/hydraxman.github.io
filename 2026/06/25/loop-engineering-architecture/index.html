Loop Engineering 火了：AI Agent 真正的架构，是这 4 个循环

很多团队做 Agent 的第一反应，还是换模型、加工具、把 Prompt 写长一点。

LangChain 最新这篇《The Art of Loop Engineering》真正有价值的地方，是把问题换了一个问法：不要只问模型能不能干活，要问这套系统有没有循环、有没有验收、有没有触发器、有没有自我改进的材料。

这就是最近开始被频繁提到的 Loop Engineering。

它不是一个新框架名，也不是 Prompt Engineering 的包装词。更准确地说，它是在给 Agent 设计“运转结构”：任务怎么进来，模型怎么行动，结果怎么验证，失败怎么返回，生产数据怎么反过来改进系统。

如果用一句话概括：Prompt 是你对模型说的话，Loop 是系统反复推动模型做事的机器。

第一层：Agent Loop，让 AI 不只是聊天，而是真的动手

最底层的循环，其实大家都熟悉。

用户给一个目标，模型拿到上下文，决定下一步该调用什么工具；工具返回结果后，模型再看一眼，继续调用工具，直到它认为任务完成。

这就是 LangChain 文中说的基础 Agent Loop：模型在循环中调用工具，直到任务完成。LangChain 的 create_agent 就是这个基本形态。

放到一个文档维护场景里，它可能是这样工作的：收到“帮我更新 API 文档”的请求后，Agent 去拉仓库、读文件、改 Markdown、检查引用、最后开一个 PR。

这一步解决的是“AI 有没有手脚”。

但它有一个很大的坑：会做动作，不等于做对事情。

一个 Agent 可以很勤奋地读文件、改文档、开 PR，看上去忙得像个工程师。但链接可能是坏的，CI 可能没过，diff 可能改飞了，甚至需求本身可能被它理解错。

所以，只靠 Agent Loop，最多得到一个“会行动的聊天机器人”。要进入生产系统，还差第二个循环。

第二层：Verification Loop，别让 Agent 自己宣布“我完成了”

真正的分水岭，是 Verification Loop。

它的逻辑很朴素：Agent 做完以后，不直接相信它，而是让一个验证器检查结果。通过就结束，失败就把反馈丢回去，让 Agent 重试。

这层循环可以是确定性的，比如测试、链接检查、schema 校验、CI；也可以是模型评审，比如 LLM-as-judge 按 rubric 打分。LangChain 在文章里提到的 RubricMiddleware，就是把这种运行时评分和修订循环放进 Agent 执行过程里。

文档 Agent 的例子很典型：每次修改后，系统可以检查三件事：

  • 所有链接是否可访问；
  • CI 是否通过；
  • diff 是否只改了这次请求范围内的内容。

这一步的意义，不是“再让一个模型夸一遍”。

它真正做的是把 Agent 从“自我汇报系统”变成“证据驱动系统”。

程序员不能说“我感觉修好了”就合并代码，至少要跑测试。Agent 也一样。它不能只说“任务完成”，而要拿出证据：测试绿了、页面变了、API 返回对了、文件 diff 对得上。

当然，验证会增加成本和延迟。LangChain 也明确提到，这个代价在质量比速度更重要的生产场景里通常值得付。

更直白一点：没有 Verification Loop 的 Agent，越自动化越危险。

第三层：Event-driven Loop，让 Agent 从“被叫醒”变成后台组件

前两层解决的是一次任务怎么做、怎么验。

但真实业务里，Agent 不可能永远等人打开聊天框叫它。很多工作本来就是事件驱动的：有新工单、有新文档、有 webhook、有定时任务、有群消息、有监控报警。

Event-driven Loop 要做的，就是把 Agent 接到这些事件上。

它的结构并不复杂：事件触发 Agent，Agent 执行任务，验证器检查结果，然后系统更新真实状态。

到这一层，Agent 的角色变了。

它不再只是一个聊天窗口，而是组织系统里的后台组件。比如：

  • 新 issue 出现后，自动判断是不是文档问题；
  • 每天定时扫描知识库，找过期链接；
  • Slack / 飞书里有人发需求时，产出初稿或 PR；
  • 监控报警出现后，先跑一轮排查并附上证据。

LangChain 提到，LangSmith Deployment 可以用 cron、webhook 触发 Agent；Fleet 可以用 channel 和 schedule 让 Agent 在团队协作环境里运行。文章里还提到了 OpenClaw heartbeats 这种 cron 触发的主动助手形态。

但这一层也最容易被误用。

因为一旦 Agent 常驻运行，它真的会去改系统、发消息、建工单、动数据。这里必须有权限边界和人工确认：删库、付款、发外部邮件、公开发布、修改生产配置，这类动作不能随便全自动。

Event-driven Loop 的正确用法，不是让 Agent 获得无限自由，而是让它在清楚边界里处理可自动化的那一段。

第四层：Hill-climbing Loop，让每次失败都变成下一版系统的材料

最有意思的是第四层：Hill-climbing Loop。

前三层让 Agent 能做事、能被检查、能自动触发。第四层问的是：这套 Agent 系统怎么持续变好？

答案不是靠玄学调 Prompt，而是靠 trace。

Trace 就是 Agent 的运行轨迹：模型每一步说了什么，调用了什么工具，工具返回了什么，哪里失败了，验证器给了什么反馈，token 花了多少，延迟是多少，最后有没有通过。

LangChain 另一篇关于 trace 的文章里有一句判断很准：在传统软件里，代码记录应用；在 AI 系统里，trace 记录行为。代码只能告诉你 Agent 被允许做什么，trace 才告诉你它在某次真实运行中到底做了什么。

Hill-climbing Loop 的流程大致是：收集生产 trace，找出失败模式，把失败变成评估样例或改进建议，然后改 harness，再重新评估和部署。

这里的 harness，指的是模型外面的整套“外壳”：Prompt、工具列表、工具描述、上下文策略、记忆方式、验证规则、人工审批点、重试逻辑。

很多 Agent 的提升，并不是模型权重变强了，而是这个外壳变得更适合任务。

比如：

  • 发现 Agent 总是改错文件，就调整检索和上下文选择；
  • 发现它总是漏跑测试，就把测试变成强制验证器；
  • 发现它经常在某类任务上超时，就加停止条件和分解策略；
  • 发现人工经常指出同一种错误，就把它沉淀成 rubric 或 eval。

这才是 Loop Engineering 最接近“工程”的地方：不是靠一次灵感写出完美 Prompt，而是用真实运行数据，一轮轮把系统磨稳。

这 4 个循环叠起来，才像一个生产级 Agent

把四层放在一起看，Loop Engineering 的架构并不神秘：

循环 解决的问题 关键组件 最容易踩的坑
Agent Loop 让模型能行动 模型、工具、状态、停止条件 动作很多，但目标没完成
Verification Loop 判断结果是否正确 测试、rubric、CI、grader 只让模型自评，没有外部证据
Event-driven Loop 自动进入业务流 cron、webhook、消息通道、队列 权限太大，自动犯错
Hill-climbing Loop 持续改进系统 trace、eval、人类反馈、harness 收集了日志，但没有变成改进

这四层不是“功能清单”，而是一个递进关系。

第一层让 Agent 有手脚。

第二层给它装上验收标准。

第三层把它接进真实业务。

第四层让它从每次运行里学习怎么变稳。

这也解释了为什么很多 Agent demo 看着惊艳，一上生产就不好用。它们往往只有第一层：模型会调用工具，但没有可靠验证，没有事件系统，没有 trace 驱动的改进。

一个没有验证和追踪的 Agent，本质上只是更会动手的聊天框。

真正难的不是循环，而是“完成标准”

也别把 Loop Engineering 神化。

它不是把 Agent 变成全自动员工的魔法。它解决的是系统结构问题，不是模型能力上限问题。

最难的地方，往往是 Verification Loop：你得先定义什么叫“做完了”。

写代码可以跑测试，改文档可以查链接，数据清洗可以验 schema，工单分类可以和人工标注比对。但如果任务是“写一篇有洞察的文章”“判断这个产品战略是否正确”，验证就会困难得多。

LLM-as-judge 可以辅助，但不能替代所有证据。尤其在高风险任务里，确定性检查、外部状态查询、人工审批，仍然比模型自评更可靠。

所以 Loop Engineering 最适合的，不是所有任务，而是那些输入、动作、验收标准都能定义清楚的流程：代码修复、文档维护、数据处理、内部知识库、运维巡检、工单流转、报表生成。

越能定义完成标准，循环越有价值。

未来的 Agent 工程师，写的不是一句 Prompt

LangChain 这篇文章真正提醒人的地方，是它把 Agent 工程师的工作从“调模型输出”推到了“设计系统运转”。

以前大家问：Prompt 怎么写，模型怎么选，工具怎么接。

现在更重要的问题是：任务怎么触发，失败怎么发现，证据怎么留下，权限怎么收住，trace 怎么变成下一轮改进。

这其实更像传统软件工程，只是我们现在要包住一个不确定的模型。

模型是发动机，Prompt 是驾驶指令，Loop 才是传动、刹车、仪表盘和维修系统。

未来靠谱的 Agent 团队，拼的可能不是谁的 Prompt 更玄学，而是谁的循环更扎实。

AI 能不能干活，看模型；AI 能不能长期替你干活，看 Loop。
