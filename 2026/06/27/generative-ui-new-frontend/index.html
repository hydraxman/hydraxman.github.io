生成式 UI 正在变成新的前端：别再让 Agent 只会回一段话

过去一年，很多 AI 产品都有一个共同的问题：模型越来越会干活，界面却还停在聊天框里。

用户问“帮我分析这笔支出”，Agent 回一大段文字；用户问“帮我比较几个航班”，Agent 还是回一串列表；用户问“把这个 API response 可视化一下”，Agent 继续用 Markdown 解释。

这很像让一个会开车的人，只能隔着电话告诉你路线。

真正的变化不是 Agent 会不会回答，而是 Agent 能不能直接把下一步界面画出来。

这就是最近被频繁讨论的生成式 UI。它要解决的不是“前端还需不需要写”，而是“前端从固定页面，变成 Agent 和用户共同操作的动态界面”。

原文《生成式 UI 正在成为新的前端》抓住了一个关键点：生成式 UI 不是一种做法，而是一条谱系。大致可以分成三类：Controlled、Declarative、Open-ended。

这三类背后的取舍，比很多团队想象得更重要。

先把协议层级讲清楚：MCP、A2A、AG-UI 不是一回事

讨论生成式 UI，最容易先被几个缩写绕晕。

MCP、A2A、AG-UI、A2UI、MCP Apps，名字都像协议，但它们不在同一层。

可以先用一句话分开：

MCP 让 Agent 连接工具；A2A 让 Agent 连接 Agent；AG-UI 让 Agent 连接用户界面。

再往下一层看，AG-UI 和 A2UI 也不是竞争关系。

AG-UI 是 CopilotKit 推动的 Agent–User Interaction 协议，定位是“用户侧应用和 Agent 后端之间的双向运行时连接”。它负责把消息、状态更新、工具调用、UI 事件这些东西实时传来传去。

A2UI 则是 Google 推出的声明式 UI 格式。它解决的是“Agent 到底要展示什么”：卡片、表单、列表、布局、数据绑定，都可以变成结构化消息，而不是一段可执行代码。

所以更准确的理解是：AG-UI 是管道，A2UI 是管道里流动的一种 UI 内容格式。

Google 在 A2UI 官方介绍里给过一个很好的判断：远程 Agent 不能直接操作你的 DOM，它只能发送消息。问题是，这条消息既要像数据一样安全，又要像代码一样有表达力。

这句话其实点破了生成式 UI 的核心矛盾。

如果直接让 Agent 写 HTML，表达力很强，但品牌、安全、交互一致性都难控；如果只让它选固定组件，又很稳，但长尾需求会迅速把组件库撑爆。

三种模式，就是围绕这个矛盾展开的三种答案。

第一种：Controlled，把 Agent 关在你写好的组件里

Controlled 是最容易落地的生成式 UI。

前端工程师先写好一批组件，比如费用图表、航班卡片、订单状态、任务列表。然后把这些组件注册成 Agent 可以调用的“工具”。Agent 不负责写 UI，只负责判断：现在该展示哪个组件，以及传什么参数进去。

它的好处非常明显。

设计系统完全在前端手里。组件怎么排版、按钮怎么动、颜色怎么跟品牌一致，都由工程师和设计师决定。Agent 只是选择和填数据。

这很适合高价值、低数量、强品牌控制的场景：财务卡片、审批流程、仪表盘关键指标、客服工单详情。

但 Controlled 有一个天花板。

每多一个可展示组件，就多一个工具定义、参数 schema 和说明。组件少时很稳，组件一多，Agent 上下文里塞满相似工具，选择错误就开始变多。

原文提到一个很现实的数字感：如果一个组件工具描述加 JSON schema 大约几百 tokens，几十个组件很快就会把每轮请求成本抬上去。这个方向不一定精确到某个固定数值，但趋势是确定的：Controlled 的成本，会随着组件数量线性增长。

所以 Controlled 不是错，它只是适合“少而关键”的界面。

如果你有三个核心流程，应该用它。如果你有三百种卡片，就别硬塞。

第二种：Declarative，让 Agent 输出 schema，而不是选组件

Declarative 是更像“新前端”的部分。

在这种模式里，Agent 不再从一堆固定工具里选一个，而是输出一份结构化 UI 描述：这里有一个列表，列表里有若干卡片，卡片上有标题、价格、按钮、状态字段。

前端则维护一个组件 catalog。Agent 只能使用 catalog 里允许的组件，应用负责把 schema 映射成 React、Flutter、Angular 或其他框架里的真实界面。

这也是 A2UI 的核心价值：Agent 负责表达意图，前端负责渲染边界。

它比 Controlled 更适合长尾场景。

比如搜索结果、表单、推荐卡片、Dashboard 小组件、旅行行程、商品比较。你不可能为每一个组合都预写一个工具，但可以给 Agent 一个组件词汇表，让它在边界内组合。

这套模式还有一个关键好处：组件库扩张时，Agent 不一定要看到每个具体组件工具。它看到的是一种更抽象的“渲染能力”，成本增长更平坦。

但代价也很明确。

你把一部分布局权交给了 Agent。即使有 catalog，有 schema，有校验，它也可能在某次输出里把优先级排错，把组件组合得不符合产品预期，或者在动态 schema 里生成需要修复的结构。

所以 Declarative 的工程重点不是“让模型自由发挥”，而是三件事：

  • catalog 要小而清楚，组件边界不能含糊；
  • schema 要能验证，错误要在进入渲染层前被挡住；
  • 关键页面要有降级方案，不能让用户看到空白或畸形 UI。

这类系统看起来像前端，但更像一套 UI 合约系统。

第三种：Open-ended，让 Agent 直接生成界面，但必须关进沙盒

Open-ended 是最炫，也最危险的一类。

这里没有固定组件，也没有 catalog。Agent 可以直接生成 HTML，或者通过 MCP Apps 这类机制拿到外部应用提供的 UI surface，再在沙盒 iframe 里展示出来。

它的优势是表达力极强。

用户说“把这个网络拓扑画出来”，Agent 可以画；用户说“给这段 JSON 做个临时可视化”，Agent 可以临时做；用户说“做一个一次性的交互小工具”，Agent 也可以马上拼出来。

这类场景很适合“可丢弃界面”：只看一次、只为当前任务存在、不要求下次还长一样。

但它不适合作为主界面。

因为主界面需要稳定的品牌、稳定的可访问性、稳定的交互习惯。今天像一个 SaaS Dashboard，明天像一个游戏菜单，后天像一个老 iOS 弹窗，这不是“灵活”，这是产品人格分裂。

安全边界也更麻烦。iframe sandbox 过紧，按钮和表单可能不能用；过松，又可能带来更大的风险。A2UI 官方对比里也把 MCP Apps 归为“预构建 HTML + sandboxed iframe”的路线：隔离性强，但外观和宿主应用的融合度天然差一点。

所以 Open-ended 的正确位置不是默认方案，而是实验室、临时画布和一次性可视化。

真正的问题不是“选哪个框架”，而是你在押注谁

生成式 UI 的三种模式，本质上是三种押注。

Controlled 押注前端团队。界面最稳，但扩展最贵。

Declarative 押注 schema 和 catalog。扩展更平滑，但需要认真设计 UI 合约。

Open-ended 押注模型和沙盒。最自由，但最难保证品牌、安全和一致性。

如果业务刚开始，只有几个高价值流程，Controlled 很合适。

如果产品进入规模化阶段，需要几十种卡片、表单、状态面板，Declarative 更像长期方案。

如果只是临时探索、一次性可视化、让用户看完就走，Open-ended 才有意义。

最糟糕的做法，是不知道自己已经选了模式。

很多团队一开始因为框架默认支持，就用 Controlled；组件一多，成本和选择错误开始爆炸；然后看到 Open-ended demo 很酷，又直接跳过去，最后发现产品风格完全失控。

中间缺掉的，恰恰是 Declarative 这一层。

生成式 UI 不会消灭前端，但会改变前端的工作重心

“生成式 UI 是新的前端”这句话容易被误解。

它不是说以后不写前端了，也不是说 Agent 会替你做完所有界面。

真正的变化是：前端不再只交付静态页面，而要交付一套能被 Agent 调用、组合、更新、验证的界面系统。

过去前端交付的是页面。

现在更像交付三样东西：

  • 组件 catalog：Agent 被允许使用哪些 UI 积木；
  • 状态协议：Agent 和用户修改如何互相同步；
  • 验证边界：什么 schema 可以渲染，什么必须拒绝或降级。

这对前端工程师不是削弱，反而是抬高。

因为当 Agent 开始参与界面生成，真正值钱的不是会不会写一个按钮，而是能不能设计一套不会被 Agent 玩坏的 UI 运行时。

未来的前端，不只是把 Figma 还原成页面，而是把产品界面做成 Agent 可以安全操作的语言。

这也是生成式 UI 最值得关注的地方。

它不是聊天框里多几张漂亮卡片，而是 AI 产品形态的一次迁移：从“用户问、模型答”，走向“用户意图、Agent 执行、界面实时长出来”。

前端不会消失。

但前端的边界，正在从屏幕上的像素，扩展到 Agent 能理解和调用的那套 UI 语法。
