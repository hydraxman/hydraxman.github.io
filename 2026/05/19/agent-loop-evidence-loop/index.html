Agent Loop 没有魔法：真正让智能体完成任务的是 Evidence Loop

过去一年，“Agent”这个词被用得太宽：会调工具叫 Agent，会跑工作流也叫 Agent，会在浏览器里点按钮也叫 Agent。真正关键的问题其实只有一个：一个任务交给它之后，系统凭什么判断它真的完成了？

这篇文章只讲这个核心：Agent Loop 的技术原理，以及比 Agent Loop 更重要的 Evidence Loop。

我的判断先放前面：Agent Loop 本身没有魔法。它只是一个控制系统：模型负责提出下一步动作，工具和环境负责返回反馈，验证器负责判断是否继续。真正让 Agent 从“会说”变成“能办事”的，是可审计的证据闭环。

1. Agent Loop 的最小形态：Think → Act → Observe

现代 Agent 的基本循环，可以从 ReAct 论文开始理解。ReAct 把语言模型的推理与行动交错起来：模型先生成 Thought，再执行 Action，然后把外部环境返回的 Observation 送回上下文，进入下一轮。它解决的不是“模型更聪明”这个问题，而是让模型从封闭文本空间进入外部世界：搜索、查文件、跑命令、点网页、调 API。

这个闭环背后有几个关键设计点：

  • State：当前任务目标、历史消息、工具结果、临时记忆、预算。
  • Policy：通常是 LLM，决定下一步是回答、规划、调用工具，还是停止。
  • Action Space：可用工具集合，比如搜索、Shell、浏览器、数据库、编辑器、MCP 工具。
  • Observation：工具返回的结构化或非结构化反馈，比如 stdout、DOM、截图、测试日志。
  • Stop Condition：何时结束。最危险的做法是让模型自己说“完成了”。

所以 Agent Loop 不等于“LLM + tools”这么简单。它更像一个带传感器的闭环控制系统：动作没有观察就无法纠偏，观察没有验证就无法判断完成。

2. 从论文脉络看：Loop 一直在补三件事

围绕 Agent Loop 的论文大致都在补三块能力：工具使用、路径搜索、反馈学习。

WebGPT 是早期 Evidence Loop 的代表：模型使用文本浏览器搜索、打开网页、引用证据，再回答问题。它把“答案来自模型记忆”改成“答案来自外部网页证据”。

MRKL 和 Toolformer 把工具调用体系化：前者把 LLM 看成路由器，调用计算器、知识库、符号系统等专家模块；后者研究模型如何自监督学习何时调用 API、调用什么 API，以及如何吸收工具结果。

ReAct 给了最经典的 Thought / Action / Observation 形式。后来的 Agent 框架基本都逃不开这个骨架。

Plan-and-Solve、ReWOO、HuggingGPT 则在改造循环结构：不是每一步都边想边查，而是先规划任务、列工具调用，再由 worker 执行，最后汇总。好处是成本低、可并行；坏处是初始计划错了会系统性偏离，所以必须支持 re-plan。

Tree of Thoughts 和 Graph of Thoughts 把 Think 阶段从单线 Chain-of-Thought 扩展成搜索问题：维护多个候选思路，评估、剪枝、回溯、合并。它们对 Agent 的意义不是“更会写思维链”，而是让系统可以比较不同路径。

Reflexion 和 Voyager 则加入跨轮学习。Reflexion 不更新模型权重，而是把失败反馈转成语言反思，写入 episodic memory；Voyager 在 Minecraft 里维护 skill library，把成功代码片段变成可复用技能。

SWE-agent 的重点更工程：它提出 Agent-Computer Interface，说明接口设计本身就是算法的一部分。文件怎么展示、命令输出怎么压缩、编辑工具如何约束、测试反馈如何返回，都会决定 Agent 能否修复真实代码库。

3. Evidence Loop：完成不是一句话，而是一组证据

大哥关心的关键问题是“怎么算完成”。答案是：done 不能由执行者自证，必须由证据链证明。

一个可用的 Evidence Loop 至少包含六步：

  1. 定义 Done：把用户目标翻译成验收条件。比如“修复登录 bug”不是验收条件，“新增回归测试并通过 auth 相关测试”才是。
  2. 设计 Probe：决定用什么探针验证。可能是单元测试、HTTP health check、数据库查询、DOM 检查、截图、文件 hash。
  3. 收集 Evidence：保存原始日志、命令、diff、stdout/stderr、API 响应、页面状态，而不是只保存自然语言总结。
  4. 独立验证：优先用程序化 validator；开放式文本任务可以辅以 LLM-as-judge；高风险任务需要人工审批。
  5. 决策：证据足够则 done；证据不足则 retry；风险超出权限则 escalate。
  6. 反思与记忆：失败证据进入下一轮策略，但注意：reflection 帮助改进，不能替代 evidence。

这里最容易混淆的是“过程证据”和“完成证据”。

  • “我点击了提交按钮”是过程证据。
  • “订单记录已存在，状态为 submitted，订单号为 X”才是完成证据。
  • “我修改了代码”是过程证据。
  • “相关测试通过，CI 通过，diff 只涉及目标模块”才是完成证据。

过程证据说明 Agent 做过什么，完成证据证明目标已经达成。

4. 从代码看：7 层 Agent Loop 怎么长出来

为了把这个概念讲得更实一点，我做了一个配套的 Python 示例仓库：hydraxman/agent-loop-evidence-lab。它不是一个“又一个 Agent 框架”，而是一个教学用的最小实现：同一个任务循环，从 01 到 07 逐步加能力。每一层代码都尽量短，目的就是看清楚 loop 的骨架怎么长出来。

这张图的重点是中间第 4 层：没有 Evidence Loop，就没有可靠完成。前三层解决“Agent 怎么行动”，后四层解决“失败后怎么修正、经验怎么沉淀、最终凭什么交付”。

仓库里的 7 层升级路线如下：

层级 Loop 新增能力 关键问题
01 Basic Function Call 最小 tool call 能调用工具，但没有验证
02 Typed Tools + Errors 工具参数、错误处理 工具成功不代表任务完成
03 Plan-and-Execute 先规划再执行 计划完成不等于目标完成
04 Evidence Loop Done Definition + Validator 由证据决定 done/fail
05 Reflexion Retry 失败后反思并重试 failure 进入下一轮策略
06 Memory Agent 持久化 lesson 经验跨任务复用，也带来污染风险
07 Mini Coding Agent workspace + patch + test 接近真实 coding agent 的最小骨架

4.1 Loop 01：最小 Function Call，只是会“动手”

第一层只做一件事：模型决定调用哪个函数，工具返回结果，然后输出最终答案。

这个 loop 已经有了 ReAct 的影子：think -> act -> observe -> final。但它还不是可靠 Agent，因为停止条件非常弱：只要工具返回了东西，Agent 就说完成。这里没有 done definition，没有 validator，也没有 evidence verdict。

4.2 Loop 02：Typed Tool，把失败也变成 Observation

第二层加了工具调用的边界：参数结构、异常处理、结构化 observation。

这一步很小，但工程意义很大：错误不是中断，而是下一轮决策的输入。很多 Agent demo 一报错就崩，真正的 loop 要把错误包装成 observation，让模型有机会修正动作。

4.3 Loop 03：Plan-and-Execute，计划不是证据

第三层先生成计划，再按步骤执行：

Plan-and-Execute 的价值是把“想”和“做”拆开。复杂任务里，planner 可以先拆任务，executor 再逐项调用工具。但这里有一个常见误区：计划执行完，不代表目标完成。

比如 Agent 按计划“打开网页、点击提交、返回成功”，这只能证明它走完了流程；如果后台没有订单记录，任务仍然失败。所以从这一层开始，必须引入 Evidence Loop。

注意这里的“完成”不是 Agent 说“我改好了”，而是两条验证同时成立：

  1. RED 被复现：证明测试确实能抓住 bug，不是无效测试。

这个 RED/GREEN 证据对 coding agent 非常重要。没有 RED，可能只是跑了一个无关测试；没有 GREEN，patch 没有完成；没有 diff/log，就无法审计它到底改了什么。

在这个示例里还遇到一个很真实的工程坑：同一秒内修改 Python 文件后马上重跑 pytest，可能复用旧 .pyc 缓存，导致测试仍看到旧代码。所以示例里 patch 后会清理 __pycache__。这类细节说明：Agent Loop 不是写个 while 就完事，它必须理解运行环境、缓存、文件系统和测试工具的反馈。

5. Evidence 的强弱排序

不同证据的可信度不一样。一个实用排序是：

  1. 确定性 validator：测试、schema validation、业务状态检查。
  2. 真实环境状态：数据库记录、网页 DOM、外部 API 查询、CI 结果。
  3. 原始日志和轨迹：命令、stdout/stderr、截图、diff、hash。
  4. 人工审批：成本高，但高风险场景必要。
  5. LLM-as-judge：适合开放式文本质量判断，但有 position bias、verbosity bias 等问题，不能替代测试。
  6. Agent 自评：最低，只能作为提示。

SWE-bench 和 SWE-agent 给了软件工程里的强范式：任务来自真实 GitHub issue，Agent 修改代码，最后用测试集验证 patch。WebArena 则给了网页任务里的强范式：Agent 在真实风格网站里操作，最终用 annotated program 检查目标是否完成。它们的共同点是：评价不看 Agent 说得多漂亮，而看外部环境是否达到目标状态。

6. 主流框架的 Loop 实现差异

不同 Agent 框架的核心差异，不是“有没有大模型”，而是它们怎样管理状态、工具、验证和人类介入。

LangGraph / LangChain Agents 把 Agent 做成显式图。模型节点、工具节点、中间件节点通过边连接；checkpointer 负责持久化状态；Human-in-the-loop 可以在工具调用前审批、修改、拒绝。它的强项是可控、可恢复、可观测。

OpenAI Agents SDK 和 Claude Code Agent SDK 是 runner 模式：每一 turn 里模型输出工具调用，SDK 执行工具并把结果回填；如果出现 final output、max_turns、预算限制、guardrail 或人工中断，就停止。它适合把 Agent Loop 嵌进应用。

SWE-agent / mini-SWE-agent 更极简也更锋利：核心就是模型与 shell / 文件系统 / 测试环境之间的 action-observation loop。它说明一个事实：对 coding agent 来说，最重要的工具不是花哨 UI，而是可靠的编辑、搜索、运行测试和清晰错误反馈。

OpenHands 使用 sandbox runtime，把 action 扔进隔离环境执行，再返回 observation。它的价值在于把真实开发环境容器化，让轨迹、文件修改、命令输出都可追踪。

OpenClaw 的公开文档展示的是 session/run + event stream + hooks 的架构：assistant、tool、lifecycle 事件贯穿一次运行；before_tool_call / after_tool_call / tool_result_persist 这类 hook 可以拦截、审计和持久化工具调用。它的重点更像“Agent 运行时与消息网关”，证据链天然落在 event stream 和 tool result 上。

AutoGPT Platform 则已经从早期“单智能体自己循环”演进到工作流/DAG：Block 是动作节点，graph executor 管节点队列。它更像低代码自动化平台，而不是纯 ReAct agent。

7. 不同路径：单线、规划、搜索、图和多 Agent

Agent Loop 不是只有一种跑法。

单线 ReAct 最简单：每步观察后决定下一步。优点是灵活；缺点是慢、容易局部贪心、上下文膨胀。

Plan-and-Execute 先全局规划，再执行工具。优点是成本低、可并行；缺点是计划一开始错了就会一路错，所以需要 re-planning。

Tree / Graph Search 同时探索多条路径。适合数学、策略、复杂诊断、研究任务，但成本更高，需要 evaluator。

Reflexion Loop 把失败反馈写入记忆，下次尝试少踩坑。适合有多次尝试机会的任务，不适合一次性高风险操作。

Multi-agent Loop 把 planner、researcher、executor、critic、verifier 分开。好处是职责清晰；坏处是协调成本和错误传播更高。真正有价值的多 Agent，不是“多几个角色聊天”，而是让验证者与执行者分离。

9. 结论：Agent 的边界由证据定义

Agent Loop 的本质不是让模型无限循环，而是让模型在外部世界中获得反馈并持续修正。真正难的地方不是写一个 while loop，而是设计：

  • 工具是否足够可控；
  • observation 是否足够清晰；
  • verifier 是否独立；
  • evidence 是否可回放；
  • 失败是否能转成下一轮策略；
  • 高风险动作是否有人类审批。

所以，“Agent 能不能完成任务”不是一个模型能力问题，而是一个系统工程问题。模型决定下一步，工具改变世界，环境返回事实，验证器决定是否完成。没有 Evidence Loop 的 Agent Loop，只是会调用工具的聊天机器人；有了 Evidence Loop，它才开始像一个可靠的执行系统。
