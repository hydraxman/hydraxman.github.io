Agent 编排与 Agent Loop：40 篇最新论文里能落地的工程判断

一句话：2026 年的 Agent 论文已经从”我做了个 Demo”转向”我承认这玩意儿在生产里有坑”，本文挑了 arXiv 上最近一个月的 40 篇相关论文（20 篇 Agent Orchestration + 20 篇 Agent Loop），试着用工程师听得懂的话讲清楚——什么在收敛、什么还在打嘴炮、什么是噱头。

0. 为什么要写这篇

如果你打开 GitHub 搜 “agent framework”，会看到一个荒诞的数字：LangGraph、CrewAI、Google ADK、OpenAI Agents SDK、Semantic Kernel、Strands、LlamaIndex 加起来超过 29 万星（来自 Dennis et al. 2026, arXiv:2605.22502 的统计）。

但真正在生产环境跑稳的多 Agent 系统？根据 Apostolou et al. 2026 (arXiv:2605.14675) 对 12 家企业 16 位工程师的访谈：

  • 7 家停在 Level 1（AI 助手）
  • 4 家停在 Level 2（AI 替代单点任务）
  • 只有 1 家进到 Level 3（Multi-Agent Orchestration）

这就是现状——框架的繁荣度和生产成熟度之间差了至少 1 个数量级。

本文不堆 paper 摘要，目标是回答两个问题：

  1. Agent 编排（Orchestration） 这一年到底在迭代什么？
  2. Agent Loop（单体执行循环） 还有没有比 ReAct 更值得抄的东西？

文末给出工程取舍清单和论文打包下载。

一、概念厘清：Orchestration ≠ Loop

很多人把这两个词混着用，先掰开：

维度 Agent Loop Agent Orchestration
关注尺度 单个 Agent 内部怎么思考 → 行动 → 观察 多个 Agent 之间怎么分工、传值、收敛
典型范式 ReAct / Reflexion / Plan-Then-Execute Generator-Evaluator / Hierarchical / Event-driven
失败模式 死循环、幻觉、token 爆炸 角色冲突、credit assignment、调度延迟
工程比喻 一个程序员的 think-code-test 循环 一个团队的 PM-Dev-QA 协作

混用的代价：你想优化 Loop，结果加了一堆 Agent；你想做 Orchestration，结果每个 Agent 还在裸 ReAct。

二、Agent Orchestration：四条值得关注的主线

主线 1：把工作流”编译进权重”，挑战外挂编排范式

这是我个人觉得最反共识、也最有杀伤力的方向。

Dennis et al. 2026 (arXiv:2605.22502) 提出 Subterranean Agent：与其把流程图喂给 GPT-5/Claude，不如把流程微调进一个小模型的权重。

他们在三个真实业务上验证：

  • 旅行预订（14 节点）
  • Zoom 客服（14 节点 + 产品知识）
  • 保险理赔（55 节点、6 个决策枢纽）

结果：接近 frontier 质量，成本降 100×。

工程意涵：

  • 如果你的 workflow 已经稳定（>3 个月没大改），LangGraph 的 DAG 其实是个负债——它每轮都要把全图 prompt 塞进 frontier 模型
  • 微调小模型把固定流程”压缩”进去，等于把热路径 JIT 了
  • 反例：流程还在天天改的产品，别去编译，徒增训练成本

主线 2：从”流水线”到”事件驱动”

Alexandrou & Pramatari 2026 (arXiv:2605.13110) 做了个 VC 尽调系统，强调一个看似常识但 99% 框架做错的事：真实业务是异步事件流，不是同步管道。

他们用 event-driven orchestration 替代了流水线，组合 LLM + 实时 web 检索来合成 VC 报告。

类似思路出现在：

  • LongSeeker (arXiv:2605.05191)：长程搜索 Agent 的”弹性上下文编排”——根据任务阶段动态扩缩 context，而不是一直累加
  • Response-Conditioned Parallel-to-Sequential (arXiv:2605.15573)：根据上一步响应动态切换并行/串行模式，而不是出厂就硬编码

工程意涵：LangGraph 那种”静态图 + 状态机”在长任务上会被打爆，越来越多的工作转向”调度策略本身可学”。

主线 3：用 RL 学编排策略（LEMON 路线）

LEMON: Learning Executable Multi-Agent Orchestration via Counterfactual RL (arXiv:2605.14483) 是最近这波里把 RL 用得最像样的：

  • 用反事实信号做 credit assignment（解决多 Agent 经典痛点：到底是哪个 Agent 拖了后腿？）
  • 联合学习角色设计 + 容量分配 + 依赖关系
  • 比手工搭的 CrewAI/AutoGen baseline 在质量和成本上都有显著优势

相关的 SkillFlow (arXiv:2605.14089) 走的是递归技能进化路径，专门攻”reward 最大化时的策略崩塌”和”高方差梯度”。

工程意涵：如果你已经在 prompt 上调到极限、再加一个 Agent 也不见效，该考虑用强化学习把编排策略本身优化掉了——但这需要一个能跑通的离线评测环境，不便宜。

主线 4：领域多智能体框架的爆发

不是新方法论，但值得点名——证明这个方向真在落地：

  • A3D (arXiv:2605.15237)：硬件加速器自主设计
  • PetroGraph (arXiv:2605.15028)：油藏历史拟合（SPE1 误差降 95%）
  • EngiAI (arXiv:2605.19743)：工程设计多 Agent benchmark
  • AgentNLQ (arXiv:2605.19010)：通用 NL2SQL Agent
  • IndusAgent (arXiv:2605.20682)：开放词表工业异常检测
  • buddyMe (arXiv:2605.16821)：实测 ReAct loop 带来 ~30% 冗余工具调用

最后这条特别值得划重点——这是少有的论文敢直说：”ReAct 在生产里就是会产生 30% 的废调用“。

三、Agent Loop：ReAct 不是终点，但替代者还没跑出来

流派 1：质疑 ReAct，主张”先 Plan 后 Execute”

Web Agents Should Adopt the Plan-Then-Execute Paradigm (arXiv:2605.14290) 的论点非常硬：

ReAct has become the default architecture across LLM agents… We argue it is the wrong default for web agents.

理由：网页内容在运行时才出现，ReAct 每一步都要 LLM 重新判断 DOM，token 烧得吓人。先承诺一段任务专属程序，再 commit 执行，速度和稳定性都更好。

AutoRPA (arXiv:2605.21082) 把这个思路推到极端：从一次交互里合成 GUI 自动化代码，下次直接执行确定性脚本。

工程类比：ReAct 是解释执行，Plan-Then-Execute 是 AOT 编译。重复任务一定选后者。

流派 2：给”经验”一个数据结构（Skill / Memory）

Voyager 那套”Agent 自己积累技能库”的思路一直没真正跑出来。这波三篇值得看：

  • Ratchet (arXiv:2605.22148)：直接打脸 Voyager 路线——LLM 自己写的 skill 提升 +0.0pp，人工 curate 的提升 +16.2pp。瓶颈不在生成，在卫生（hygiene）。Ratchet 是个极简的 skill 卫生协议，让自演化系统不再越演化越烂。
  • Skill Programs (arXiv:2605.17734)：把技能从”文本建议”升级为可执行程序，带显式触发条件
  • LOOP Skill Engine (arXiv:2605.14237)：一次性录制 + 确定性回放，99% 成功率 + 99% token 节省

Ratchet 那个 0.0pp vs 16.2pp 的对比应该写进所有 Agent 框架的 README——不要让 LLM 自己往技能库里写垃圾。

流派 3：Loop 里的”搜索”被重新审视

Deep Research 类产品火了之后，Agent 内部的”搜索循环”成了 bottleneck。

  • Is Grep All You Need? (arXiv:2605.15184)：在 Agent 上下文里，**grep 居然能打败花哨的 RAG**——因为 Agent 有迭代能力，简单工具反而好用
  • Pi-Serini (arXiv:2605.10848)：BM25 + 前沿 LLM 在 agentic search 里足够好（再次质疑向量检索的必要性）
  • Context Gathering Decision Process (arXiv:2605.07042)：把 agentic search 形式化成 POMDP，给”什么时候停止找”一个理论框架
  • Argus (arXiv:2605.16217)：单条 ReAct rollout 信息密度太低，搞并行证据汇总

工程结论：先用 grep + BM25 跑通基线，再上向量检索——很多时候你根本不需要它。

流派 4：反思与反馈循环（Reflexion 后传）

  • A-ProS (arXiv:2605.18073)：竞赛编程场景下的多模型反馈循环，证明”执行反馈”比单纯 self-reflection 强
  • BALAR (arXiv:2605.05386)：贝叶斯主动推理——Agent 不再被动应答，而是主动问”我缺什么信息”
  • OLIVIA (arXiv:2605.11169)：在 ReAct 之上做 inference-time 在线学习，连续任务里小错误不再累积

流派 5：上下文管理与长程记忆

Agent Loop 跑长了，最终都死在 context window 上。

  • Structured Memory for Ultra-Long Video (arXiv:2605.08271)：超长视频的结构化记忆
  • LongSeeker (arXiv:2605.05191)：长程搜索的弹性上下文
  • Compound LLM Agent in Adversarial POMDP (arXiv:2605.16205)：把”看什么 / 怎么想 / 怎么分解”作为三个独立设计维度系统研究

四、把上面 40 篇浓缩成 7 条工程建议

写给正在踩坑的工程师，按优先级排：

  1. 先问自己：你需要的是 Workflow 还是 Agent？ 流程稳定 → 编译成代码或微调到小模型权重里（Dennis 路线），别套 LangGraph。
  2. ReAct 是默认值，不是答案。 网页 / RPA / 重复任务，全部上 Plan-Then-Execute。预期能省 50%+ 的 token。
  3. 多 Agent 系统先做评测再做架构。 没有 counterfactual credit assignment（LEMON 那种），加 Agent ≈ 加 bug。
  4. Skill 库必须 human-in-the-loop curate。 Voyager 那套”自动累积”目前数据上是 +0.0pp，别折腾。
  5. 检索从 grep / BM25 起步。 99% 的 agentic search 场景不需要 embedding。
  6. 上下文要会”收缩”，不能只会”累加”。 用 LongSeeker / 结构化记忆思路，每个阶段裁剪一次。
  7. Loop 里加一个”该停了”的判断。 POMDP 视角（Kausik 2026）给的最大启示：Agent 死在不知道何时停，而不是不知道下一步做什么。

五、还在打嘴炮的方向

为了不只夸论文，点几个我觉得当前不值得抄的方向：

  • 过度复杂的 hierarchical 多 Agent（5+ 角色）：除非有 RL 学过编排，否则手工设计的层级几乎一定收益递减
  • 完全自演化 skill 库：Ratchet 已经证伪
  • Self-Refine 无限套娃：A-ProS 类工作显示执行反馈 >> 纯 self-reflection
  • 把所有东西塞进单个 frontier model 的 context：成本高且不抗变更（Dennis 那篇专门讲这个）

七、结语

2026 年 5 月这一批论文的共同氛围是：冷静。

  • 不再有”我做了个 AGI 雏形”的宏大叙事
  • 取而代之的是”我做了个系统，承认它有 30% 的浪费、5% 的失败、和 13%~95% 的提升空间”
  • 框架党的 29 万 GitHub 星和企业实际 Level 3 落地数（1/12）之间的鸿沟，是这一年最诚实的注脚

工程上最值钱的一句话仍然没变：

能用代码解决的，不要用 Agent。能用一个 Agent 解决的，不要用一群。

剩下的，再谈编排和 Loop。
