Foundry Toolbox 没有魔法：所谓省 90％ Token，本质是别把几百个工具一次性塞给 Agent

微软 AI Agents Service 负责人 Jeff Hollan 最近在 X 上发了一个 demo：在 Microsoft Foundry 里用 Toolbox 接管长运行 Agent 的工具调用后，输入 token 从 4676 降到 467，少了约 90%。

这个数字很抓眼球，但我不建议把它理解成什么 Agent 技术突破。

更准确的说法是：原来的做法太浪费了。

如果一个 Agent 有上百个工具，你每次都把所有工具名称、用途、参数 schema、鉴权说明、返回结构塞进上下文，token 不爆才怪。Foundry Toolbox 做的事情并不玄学：它把这些工具先收进一个由 Foundry 托管的工具箱，再通过一个 MCP-compatible endpoint 暴露给 Agent。Agent 不再一上来看到完整菜单，而是按任务需要逐步发现和取用工具。

这就是微软说的 progressive disclosure。中文可以叫“渐进式披露”，但说白了就是：别一次性把所有东西都扔给模型。

它到底是什么

Foundry Toolbox 不是一个新的推理框架，也不是 MCP 的替代品。

它更像是 MCP 工具层上面的一个企业级网关：

官方架构图大概就是这个意思：

传统方式里，Agent 直接绑定一堆工具。每个工具都要把描述交给模型：这个工具叫什么、能干什么、参数是什么、哪些字段必填、返回什么格式。工具少的时候问题不大，工具多了以后，prompt 里大半都是工具说明。

Toolbox 换了一种组织方式：工具还是那些工具，但 Agent 只接一个入口。入口背后由 Foundry 管理工具集合、连接、版本和调用方式。

所以 4676 到 467 这个 token 下降，并不证明 Toolbox 有什么神奇压缩算法。它证明的是：把几百个工具 schema 全塞给模型，本来就是一个很差的 baseline。

90% token 节省，哪里有噱头，哪里有价值

这件事有噱头成分。

如果对比对象是“Agent 每次拿到全部工具描述”，那省 90% 很容易成立。你只要别把无关工具放进上下文，token 当然会降。这个思路在软件工程里并不陌生：懒加载、索引、路由、服务目录、API gateway，都是类似思想。

但它也不是完全没价值。

关键在于，Agent 工具调用的问题不只是 token。真正麻烦的是这些东西：

  • 哪些工具允许被哪个 Agent 用？
  • GitHub、Azure DevOps、Search、内部 API 的凭据放哪里？
  • 工具 schema 改了以后，几十个 Agent 怎么升级？
  • 谁调用了高权限工具，怎么审计？
  • 某个工具出问题，怎么回滚到旧版本？

如果只看“省 token”，Foundry Toolbox 确实像包装概念。可如果从企业 Agent 平台角度看，它解决的是工具治理问题。

这也是我觉得这东西比较准确的定位：

Foundry Toolbox 不是 Agent 的大脑升级，而是 Agent 工具层的平台化。

它的价值不在“模型突然少看 90% token”，而在于工具不再散落在每个 Agent 项目里。工具变成了一个可复用、可版本化、可集中鉴权的资产。

和普通 MCP server 的区别

MCP 是 Model Context Protocol，可以理解成模型和外部工具之间的标准接口。普通 MCP server 更像一个工具服务：你自己部署、自己鉴权、自己维护、自己接 Agent。

Foundry Toolbox 不改变 MCP 的基本思想，它是在 MCP 之上加了一层云厂商托管能力：

它提供的不是“协议创新”，而是这些工程能力：

  1. 工具集合集中管理；
  2. 一个 MCP-compatible endpoint 给 Agent 消费；
  3. connection 和 credential 交给 Foundry 管；
  4. toolbox 可以版本化；
  5. 不同 Agent runtime 可以复用同一个工具箱。

这就有点像 API Gateway 之于 HTTP API。HTTP 早就有了，但企业还是需要网关来做鉴权、路由、限流、观测和治理。

Foundry Toolbox 对 MCP 的意义也是类似的：MCP 解决“怎么接工具”，Toolbox 解决“企业里怎么管一堆工具”。

怎么安装和试用

当前 Toolbox 还在 Foundry 的 preview 体系里。使用路径有三种：Foundry 门户、VS Code Foundry Toolkit，以及 SDK / REST API。

最直接的是在 Microsoft Foundry 里进入 Tools / Toolboxes，创建一个 toolbox，把需要的工具加进去，然后生成 endpoint。

生产环境里还要考虑三件事：

  • 不要把高权限工具直接暴露给 Agent；
  • 删除、发邮件、转账、发布内容这类动作要加人工审批；
  • toolbox version 升级要灰度，不要直接改默认版本影响所有 Agent。

我的判断

Foundry Toolbox 不是革命，至少现在不是。

它更像是微软把 MCP 工具生态收进 Azure AI Foundry 后，补上的一个企业工具编排层。营销上会强调“90% token reduction”，因为这个数字好传播。但技术本质没那么神秘：少传无关 schema，按需暴露工具，token 就下来了。

真正值得看的不是这个 90%，而是后面的治理层。

如果你只是做一个个人 Agent，接三五个工具，Toolbox 意义不大。自己写 MCP server 或者直接绑定工具就够了。引入 Foundry 反而增加平台依赖。

但如果你在企业里做几十个 Agent，每个 Agent 都要接 GitHub、DevOps、CRM、搜索、内部知识库、审批流、工单系统，那 Toolbox 这类东西迟早会出现。因为工具一多，问题就从“怎么调用”变成“怎么管理”。

所以我会把它定义成：

一个有营销包装的、但方向正确的 Agent 工具治理层。

别把它当魔法，也别完全忽略它。

它没有让 Agent 更聪明。它只是提醒我们：Agent 工程里，很多成本不是模型产生的，而是我们把系统设计得太粗糙。
