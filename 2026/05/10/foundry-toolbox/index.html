Foundry Toolbox 深度分析：Agent 工具调用为什么能省 90％ Token？

微软 AI Agents Service 负责人 Jeff Hollan 最近展示了一个很有代表性的 demo：在 Microsoft Foundry 的长运行 Agent 场景中，使用 Foundry Toolbox 接管工具调用后，输入 token 从 4676 降到 467。

这个数字不是一个模糊宣传口径。按原始数字计算：

也就是说，输入 token 减少了约 **90.01%**，工具上下文体积约缩小到原来的 1/10。

这背后不只是一次省 token 的小优化，而是一个更大的 Agent 工程问题：

当一个 Agent 拥有几十个、上百个工具时，是否真的应该把所有工具描述一次性塞进上下文？

Foundry Toolbox 给出的答案是：不应该。

它的核心机制叫 Progressive Disclosure，中文可以理解为“渐进式披露”：Agent 不需要一开始吞下全部工具描述，而是先接入一个统一入口，再按任务需要动态发现、加载和调用当前相关的工具。

一、Agent 工具调用为什么会爆 Token？

传统 Agent 工具调用通常是这样的：

每个 Agent 直接绑定一批工具，例如：

  • Web Search
  • Code Interpreter
  • File Search
  • Azure AI Search
  • GitHub API
  • Azure DevOps
  • Teams
  • 内部业务 API
  • 各类 MCP Server
  • OpenAPI 工具
  • Agent-to-Agent 工具

MCP 是 Model Context Protocol，可以理解成一种让模型和外部工具、数据源标准化交互的协议。它解决的是“工具如何被模型发现和调用”的接口问题。

但无论是 MCP 工具、OpenAPI 工具，还是云厂商内置工具，只要要给模型调用，就通常需要给模型一段工具描述，包括：

  • 工具名
  • 工具用途
  • 输入 schema
  • 参数说明
  • 返回结构
  • 调用限制
  • 鉴权要求
  • 审批策略

5 个工具还好。50 个、100 个工具就会变成一个非常大的上下文负担。

更麻烦的是：大多数任务其实只需要其中两三个工具。

传统方式却常常让模型每次推理都先“看一遍完整工具菜单”。这会带来几个问题：

  1. 输入 token 暴涨；
  2. 推理延迟增加；
  3. 工具选择噪声变大；
  4. 模型更容易误选工具；
  5. 每个 Agent 都重复维护工具配置；
  6. 企业权限、审计、凭据管理分散在各处。

Jeff Hollan demo 里 4676 → 467 的下降，本质上就是这个问题的缩影。

二、Foundry Toolbox 是什么？

微软官方对 Toolbox 的定义很直接：

A toolbox is a reusable bundle of tools, managed in Foundry, that agents consume through a single, consistent interface.

翻译成人话：

Toolbox 是 Microsoft Foundry 中集中管理的一组工具集合，通过一个 MCP-compatible endpoint 暴露给 Agent 使用。

更准确地说，Toolbox 是一个由 Foundry 管理、可版本化、可复用、通过 MCP endpoint 消费的工具包。

当前 public preview 阶段，微软重点开放两个能力：

能力 状态 含义
Build 已可用 在 Foundry 中选择工具、配置鉴权、发布 reusable toolbox
Consume 已可用 通过一个 MCP-compatible endpoint 动态发现和调用工具
Discover Coming soon 发现组织内已有工具，减少重复建设
Govern Coming soon 对工具调用统一做审计、策略、观测和治理

这也是它和普通“工具注册表”的差异：Toolbox 不只是收纳工具，而是把工具变成企业级可复用资产。

传统 Agent 工具调用相当于：服务员一上来给你一本 300 页菜单，还要求你把每道菜的配料、做法、过敏原都看完再点菜。

Progressive Disclosure 相当于：你先说“我想吃辣的牛肉类”，系统只展示相关菜品；你再说“不含花生”，它再进一步过滤。

工具越多，这个收益越大。

四、为什么它特别适合长运行 Agent？

Jeff Hollan 特别强调的是：

durable, long running agents come with Toolbox

长运行 Agent 和普通 Chatbot 最大区别在于：它不是一次问答，而是一个可能持续数分钟、数小时，甚至更久的任务流。

比如一个“新人入职 Agent”可能要：

  1. 创建 Entra ID 账号；
  2. 给 GitHub repo 加权限；
  3. 创建 Azure 资源；
  4. 在 Azure DevOps 创建 onboarding task；
  5. 给 Teams 发送欢迎消息；
  6. 写入 HR 系统；
  7. 等待审批；
  8. 审批后继续执行后续动作。

如果每一步都带着完整工具目录运行，token 浪费会非常明显。

Foundry Toolbox 对长运行 Agent 的价值在于：

  • Agent 状态可以持续；
  • 工具通过统一 MCP endpoint 调用；
  • 工具鉴权集中处理；
  • 工具版本集中管理；
  • 未来可以统一审计和治理；
  • Agent 不需要每次都背着完整工具目录运行。

这对企业级 Agent 非常关键。

五、Toolbox 能放哪些工具？

根据 Microsoft Learn 文档，目前 Toolbox 支持的工具类型包括：

工具类型 说明
MCP tool 接入远程 MCP Server
Web Search 联网搜索工具
Azure AI Search 企业知识库 / 索引搜索
Code Interpreter 代码执行与数据处理
File Search 文件检索
OpenAPI tool 通过 OpenAPI schema 接入 API
Agent-to-Agent / A2A tool 调用其他 Agent

  • server_label 会成为 MCP 工具名前缀；

  • require_approval 可以控制是否需要人工审批；

也就是说，Toolbox 不只是“把工具堆在一起”，还承载了命名、鉴权、审批和连接关系。

六、Foundry Toolbox 和 MCP 的关系

Foundry Toolbox 的关键设计是：

Toolbox 自己不是一个封闭 SDK，而是暴露成 MCP-compatible endpoint。

这意味着它可以被很多运行时消费：

  • Microsoft Agent Framework
  • LangGraph
  • GitHub Copilot SDK
  • Claude Code
  • Microsoft Copilot Studio
  • MCP-enabled IDE
  • 自定义 Agent runtime

微软没有把 Toolbox 做成“只能 Foundry Agent 用”的私有工具层，而是让它成为一个 MCP endpoint。

七、安装和使用 Foundry Toolbox

严格说，Foundry Toolbox 不是一个本地安装包。它是 Microsoft Foundry / Azure AI Foundry 中的云端能力。

你需要安装或准备的是：

  1. Visual Studio Code + Microsoft Foundry Toolkit；或
  2. Azure AI Projects Python SDK；或
  3. Azure Developer CLI / REST API；
  4. 一个可用的 Foundry project。

十五、它解决的是工具治理，而不只是工具调用

如果只把 Foundry Toolbox 理解成“一个 MCP proxy”，其实低估了它。

它真正要解决的是企业 Agent 落地里的几个硬问题。

1. 工具重复建设

以前每个团队都自己封装一遍 GitHub、Azure DevOps、Search、内部 API。

Toolbox 让平台团队可以集中封装，业务 Agent 直接复用。

2. 凭据分散

以前 token、API key、OAuth 配置散落在不同 Agent 项目里。

Toolbox 把鉴权放在 Foundry project connection 里集中管理。

3. 工具变更难

以前工具 schema 改了，每个 Agent 都要改代码。

现在是更新 Toolbox version，测试后 promote default version。

4. 可见性不足

企业需要知道：

  • 谁在用哪个工具？
  • 哪个工具被调用最多？
  • 哪些 Agent 有高风险权限？
  • 哪些工具需要审批？

Toolbox 的长期方向就是把这些纳入 Foundry 治理体系。

十六、和普通 MCP Server 有什么区别？

普通 MCP Server 更像一个工具服务：

Foundry Toolbox 更像一个企业工具资产层：

简单说：

MCP 是协议，Toolbox 是企业级 MCP 工具编排与治理层。

这也是微软选择 MCP-compatible endpoint 的意义：它既不丢掉开放生态，又能把企业需要的管理能力加上去。

十七、当前限制和注意事项

Foundry Toolbox 仍处于 public preview。使用时要注意：

  • Preview 功能没有正式生产 SLA；
  • 部分能力可能受区域、模型、账号权限影响；
  • 调用 Toolbox MCP endpoint 当前需要 Foundry-Features: Toolboxes=V1Preview；
  • 同一类型工具多个实例时要注意唯一命名；
  • OpenAPI 和 A2A 在不同工具链里的支持程度不完全一致；
  • 第三方 MCP server 需要自行评估权限、数据、合规和成本风险。

尤其是企业内部使用时，不要把高权限工具无审批暴露给 Agent。

十八、我的判断：这是 Agent 平台化的关键拼图

过去一年，大家都在关注：

  • 更强模型；
  • 更长上下文；
  • 更复杂 Agent 框架；
  • MCP 生态；
  • Agent memory；
  • RAG；
  • Browser use。

但企业 Agent 真正上线时，最大问题往往不是模型不够聪明，而是：

工具太多、权限太乱、鉴权太散、审计太弱、上下文太胀。

Foundry Toolbox 对应的正是这个问题。

它的价值可以概括成一句话：

把工具从“每个 Agent 的私有配置”，升级成“企业级可治理资产”。

这有点像 Kubernetes 之后大家需要 Service Mesh。

服务越来越多之后，不能靠每个服务自己处理治理、观测、安全策略；Agent 工具越来越多之后，也不能靠每个 Agent 自己管理全部工具、凭据和 schema。

Toolbox 就是在 Agent 时代补上这一层。

十九、总结

Jeff Hollan demo 里的 4676 → 467 tokens 很抓眼球，但这只是表层结果。

真正值得关注的是：

  1. Progressive Disclosure 让 Agent 不再一次性吞下全部工具描述；
  2. 单个 MCP endpoint 让 Agent 工具接入大幅简化；
  3. Toolbox versioning 让工具变更可以灰度、测试、提升默认版本；
  4. 集中鉴权 降低凭据散落风险；
  5. 未来治理能力 会让企业能真正管理 Agent 工具调用。

如果说 MCP 解决了“Agent 怎么标准化调用工具”，那 Foundry Toolbox 进一步解决的是：

企业如何规模化、可治理地管理 Agent 工具生态。

它不是小优化，而是 Agent 工程架构从“手工接线”走向“平台化治理”的信号。
