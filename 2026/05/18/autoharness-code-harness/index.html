AutoHarness：让大模型先写规则外骨骼

Nathan

Google DeepMind 这篇 AutoHarness: Improving LLM Agents by Automatically Synthesizing a Code Harness，表面上是在讲让 LLM 玩 TextArena 文字游戏；真正值得看的是它给 Agent 工程提供了一个很清楚的判断：很多 Agent 失败，不是因为模型不会“想”，而是因为它没有可靠的动作边界。

论文地址：https://arxiv.org/abs/2603.03329。作者来自 Google DeepMind，版本为 arXiv:2603.03329v1。下面这篇解读不把它写成“又一个大模型能力突破”，因为它更像一个工程方法论：让模型把规则、校验器、甚至策略本身写成代码，再让 Agent 在这层代码外骨骼里行动。

一句话：把“别犯规”从提示词搬进代码

论文开头给了一个很扎眼的例子：在 Kaggle GameArena 国际象棋比赛中，Gemini-2.5-Flash 的失败里有 78% 被归因于非法走子。也就是说，很多失败不是“棋下得不够好”，而是“连合法动作都没稳定做到”。

这就是 AI Planning 里所谓的 action applicability problem：在某个状态下，哪些动作是可执行的？LLM 可以背规则，也可以解释规则，但在连续行动时，它的内部世界模型会漂移，会忘状态，会幻觉出一个看起来合理但环境直接拒绝的动作。

AutoHarness 的核心处理方式很朴素：不要只靠 Prompt 说“请你遵守规则”。让 LLM 自动生成一段 Python harness，也就是夹在模型和环境之间的胶水代码，用它来验证、过滤，甚至直接生成动作。

这张 Figure 1 是整篇论文的主图。左侧是代码假设树，右侧是迭代闭环：旧代码进入 Refiner，生成新代码；新代码在环境里 rollout；Critic/Evaluator 根据非法动作、执行错误、奖励等反馈，继续推动下一轮代码修复。

这里的关键不是“多想几步”，而是把原本模糊的自然语言约束压成两个可执行接口：

propose_action 负责提出动作，is_legal_action 负责判断动作是否合法。对 Agent 工程来说，这很像给模型装了一个规则外骨骼：模型仍然可以负责策略选择，但每次行动都要先过代码边界。

三种模式：校验器、过滤器、纯代码策略

论文把 harness 分成三种形态。

第一种是 Harness-as-Action-Verifier，也是论文重点实验的模式。流程是：LLM 先提一个动作，代码判断是否合法；如果非法，就带着“illegal action”的反馈重新提示模型，直到拿到合法动作。这本质上是一个学出来的 rejection sampler：采样仍来自 LLM，但接受条件由代码控制。

第二种是 Harness-as-Action-Filter。代码先生成一组合法候选动作，再交给 LLM 排序或选择。这个模式适合“动作空间可枚举，但策略判断仍复杂”的场景，比如棋类、表格操作、API 调用参数选择。

第三种更激进，叫 Harness-as-Policy：代码不只是校验动作，而是直接决定下一步动作。也就是说，测试时可以完全不调用 LLM。论文在 16 个 TextArena 单人游戏上做了这个版本，生成的 Python policy 使用基础函数和 numpy 这类标准库，推理时成本接近零。

这三个层级很重要。它不是一个单点技巧，而是一条工程光谱：

  • 轻量：LLM 出动作，代码拦非法动作；
  • 中间：代码给合法候选，LLM 做策略选择；
  • 重型：代码直接替代 LLM 成为 policy。

它怎么“学会”这层代码

AutoHarness 把 harness 生成建模为 程序搜索，不是简单地让模型一次写完。

系统维护一棵 code hypothesis tree，也就是多份候选代码组成的树。每个节点是一版 harness。训练时，它用 Thompson sampling 在“探索新逻辑”和“改进已有可用代码”之间做权衡。LLM 在这里不是最终执行者，而是一个 mutation/refinement operator：根据失败样本和错误反馈修改代码。

论文给出的训练设置比较具体：每次迭代使用 10 个并行环境，最多 rollout 1000 步；一旦代码产生非法动作或执行失败，就终止该轮，并最多采样 5 个失败步骤喂给 Critic。训练目标主要是 legal action success rate，也就是合法动作成功率。对 verifier 模式，训练在合法动作成功率达到 1.0 或超时后结束。

Figure 2 展示了 6 个游戏的学习曲线。不同游戏差异很大：有些很快达到 1.0，有些如 Chess、Othello、GermanWhist、Cryptarithm 需要更多轮 refinement。论文报告，在 32 个用于端到端评估的游戏里，平均训练 14.5 次树搜索迭代结束，19/32 个游戏少于 10 次迭代。

这个结果的工程含义是：代码 harness 不需要理解整个世界模型，只需要在某个任务上抓住“合法动作”的结构。比如国际象棋需要 UCI 坐标解析、棋子定位、攻击检测；扫雷需要从数字约束推导安全格和雷区。这类规则用自然语言提示很容易漏，但用代码表达会稳定得多。

实验结果：小模型加外骨骼，压过大模型

论文先在 TextArena 中选取全部 1-player 和 2-player 游戏，排除了 Mafia、Codenames 这类自由文本/对话动作空间游戏，剩下 145 个游戏。为了防止 harness 只是复制 prompt 里的可用动作，作者还手动移除了部分游戏 observation 里的 “Available Moves” 提示，让 Agent 必须从状态和反馈中推断合法动作。

在这 145 个游戏上，学到的 harness 都达到了 100% legal action success rate。这点要谨慎理解：它证明的是合法动作校验/生成在这个 benchmark 上成功，不等于策略一定最优。

真正有意思的是端到端表现。

在 16 个双人游戏里，Gemini-2.5-Flash + Harness 对战 Gemini-2.5-Pro，赢了 9/16 个游戏，总胜率 **56.3%**；Gemini-2.5-Pro 总胜率为 **38.2%**。同样的方法对战原版 Gemini-2.5-Flash 时，赢了 12/16 个游戏，总胜率升到 **64.8%**。

在 16 个单人游戏上，Gemini-2.5-Flash + Harness 的平均 reward 是 0.745，高于 Gemini-2.5-Pro 的 0.707，也高于 Gemini-2.5-Flash 的 0.673。分游戏看，它在 8/16 个游戏上超过 Gemini-2.5-Pro，另有 5/16 个打平。

最激进的是 Harness-as-Policy。

Figure 5 里，纯代码策略在 16 个 TextArena 单人游戏上的平均 reward 达到 0.870，超过 Gemini-2.5-Pro 的 0.707，也超过 GPT-5.2-High 的 0.844。论文还给了一个成本对比：GPT-5.2 和 GPT-5.2-High 实验约花费 640 美元，而 Harness-as-Policy 一旦生成，测试时几乎没有 LLM 调用成本。

这个结论很锋利：不是所有任务都需要更大的模型在线思考。很多任务更需要一次性把结构提炼成可执行代码，然后反复低成本运行。

这篇论文真正重要的地方

AutoHarness 的价值不在于“让模型玩游戏更强”。游戏只是一个干净 benchmark，因为它有明确规则、明确非法动作、明确环境反馈。它真正指向的是 Agent 系统里一个更普遍的问题：LLM 的强项是生成、解释、归纳；弱项是长期一致地遵守可验证约束。

所以这篇论文给出的路线可以概括成三句话：

  1. 把约束外置：别让模型每一步都靠记忆和自我提醒遵守规则，把规则写进可执行代码。
  2. 把失败变成测试样例：非法动作、执行错误、低奖励不是简单报错，而是下一轮代码 refinement 的训练信号。
  3. 把策略蒸馏进程序：如果任务结构足够稳定，LLM 可以从在线决策者退化为离线程序合成器。

这对真实 Agent 产品很有启发。比如浏览器 Agent、办公自动化 Agent、数据库 Agent、API 编排 Agent，最危险的失败往往不是“回答不够聪明”，而是动作越界：点错按钮、提交非法参数、删除不该删的数据、调用不符合状态机的 API。AutoHarness 的思路可以转译成：先让模型写 validator、adapter、state parser、candidate generator，再让模型行动。

但边界也很清楚。

第一，它依赖环境能给出明确反馈。TextArena 可以告诉你动作非法，很多真实业务系统不会这么友好，错误反馈可能延迟、模糊，甚至有副作用。

第二，它更适合规则结构稳定的任务。论文也排除了自由文本/对话动作空间游戏，因为这类任务很难定义“合法动作”的封闭集合。

第三，代码 harness 本身也可能错。它能降低 LLM 随机犯规，但不能自动保证业务规则完整、安全、无漏洞。真实系统里仍然需要单元测试、沙箱、权限边界和人工审查。

我的判断

AutoHarness 不是“LLM 推理能力又突破了”。恰恰相反，它承认了 LLM 作为在线 Agent 的一个弱点：模型很会说规则，但不总能稳定执行规则。

它的工程实质是：用 LLM 的代码生成能力，反过来约束 LLM 的行动能力。 这比单纯换更大模型更实际，也更像下一阶段 Agent 系统会采用的路线：模型负责生成可执行结构，代码负责守边界，环境反馈负责持续修正。

如果把 Agent 看成“模型 + 工具 + 状态 + 权限”的系统，AutoHarness 其实是在提醒我们：别把 harness 当胶水脚本，它可能就是 Agent 能不能可靠落地的核心部件。
