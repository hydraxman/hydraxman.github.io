从 /goal 到 Ralph Loop：Coding Agent 都在做的'目标驱动'到底是什么

一句话：2026 年所有主流 coding agent 都在抢同一个东西 —— 让你按一次回车，它能干一整夜。Codex 把它叫 /goal，社区把它叫 Ralph Loop。本文讲清楚这套机制的工程实质、各家差异，以及它的真实边界。

0. 这次更新为什么重要

5 月 21 日 OpenAI 把 Codex 的 /goal 从实验性转成 GA（changelog），意味着这个最初在 4 月 30 日 0.128.0 才上线的功能，三周内被官方认为成熟到可以默认开启、并跨 CLI / IDE / 桌面 App / 移动端全部铺开。

中间发生了什么？最出圈的事件是 a16z 合伙人 Andrew Chen 把它扔在一个 Mac eGPU 设备驱动项目上跑了 14 小时不间断，第二天醒来还在迭代（报道来源）。他自己的评论是：”obvious it’s going to 10,000x token use.”

这不是孤立功能，而是 2026 年 coding agent 的集体转向。

1. 「目标驱动」是什么：从 Prompt 模型到 Goal 模型

OpenAI 自己在 Codex Cookbook 里给了一个极简对比：

Prompt 模型 Goal 模型
范式 ask → work → result → wait work → check → continue or complete
谁决定何时停 用户 Agent（基于完成条件 / 预算耗尽）
状态 一次性 线程级持久化，可 pause / resume / clear
完成判断 用户人工看 基于证据：测试、benchmark、文件 diff、日志

注意 OpenAI 自己反复强调一句话：Goals 不是 background autonomy，是一个 user-controlled completion contract。它是把”用户什么时候介入”这件事从每一轮挪到了”完成条件未满足时一直不介入”，但用户依然 own 整件事 —— 可以随时暂停、清除、改预算。

这区别于一般的 background agent（如 Cursor 后台任务）：后者更像把任务派到远端机器跑；Goal 是同一个线程里、用同一份上下文反复”工作 → 检查 → 工作”。

2. 起源：Geoffrey Huntley 的 Ralph Loop

Codex 团队的 Philip Corey 原话：”our take on the Ralph loop — keep a goal alive across turns, don’t stop until achieved.”

Ralph Loop 是 Geoffrey Huntley 2025 年提出的极简范式，名字来自 Simpsons 里那个憨憨的 Ralph Wiggum。核心思想暴力到不可思议：

就是个 bash 死循环，每一轮把同一份 PROMPT.md 喂给 agent。Agent 跑完一轮，下一轮重新读盘上的状态文件（fresh context，没有 compaction 噪声），继续推进。

Huntley 的判断很刺耳：传统软件工程是”Jenga 式垒砖头”，他现在的工作是编程这个循环本身。这个 idea 的工程价值有两点：

  1. 不依赖长上下文 —— 每轮重新读 spec 和当前状态，绕开了”context rot”和 compaction 副作用
  2. deterministic context allocation —— 上下文里有什么、没什么，是循环结构决定的，不是 agent 自己 summarize 出来的

Codex 的 /goal 不是 bash 死循环，而是把同一个机制做进了 agent runtime —— Simon Willison 已经扒源码指出，关键实现就是两个 prompt 模板：goals/continuation.md（决定要不要继续）和 goals/budget_limit.md（决定怎么停）。每轮 turn 结束时自动注入。

工程上看，Codex 的实现比朴素 Ralph 多了几个保护：

  • conservative dispatcher：plan-only 的轮次不触发 continuation，避免空转
  • 若某轮 continuation 没有发起任何 tool call，下一轮自动 continuation 被压制 —— 防 spin loop
  • 预算耗尽 ≠ 完成：到预算时 agent 必须 summarize 进度和 blocker，不允许伪装成功
  • 状态持久化：pause / resume / clear 全部走 user/system，model 只能 start 和 mark complete（带证据）

3. 各家在干同一件事，但路径不同

Agent 等价机制 关键差异
OpenAI Codex /goal (GA, 0.133+) 线程级、模板注入式 continuation，evidence-based 完成判断
Claude Code /goal 社区命令 / 子代理 用 自定义 slash command + subagent 编排 实现，没官方原生 loop
Cursor Background Agents / /orchestrate 跑在 远端 Ubuntu 容器，强调”派任务出去”，多任务并行；/orchestrate 递归 spawn 子 agent
Sourcegraph Amp Threads + /handoff + Oracle/Librarian 子代理 线程是一等公民，可分叉、可 handoff 到新目标，多模型协作而非单 loop
Ralph / Loopy bash while 循环 agent-agnostic，stdin 即可接入任意 CLI agent

可以看到分化：

  • Codex / Ralph 路线：单线程内反复”工作 → 检查”，强调 deterministic context
  • Cursor 路线：把任务 fan-out 到远端环境，多任务并行 + 后台执行
  • Amp 路线：线程图谱 + 多 agent 角色（Oracle 决策、Librarian 检索），强调”agent 协作拓扑”

它们解决的是同一个底层问题 —— 如何让人退出实时回路 —— 但抽象层不同。Codex 抽象在 “目标”，Cursor 抽象在 “任务队列”，Amp 抽象在 “线程组合”。

4. 写一个能跑的 /goal：模板和反模式

OpenAI 给的模板值得抄：

弱例 vs 强例（来自 cookbook）：

❌ /goal Improve performance

✅

四个工程要素：可验证的完成条件（benchmark/test）、显式约束（不能动哪里）、迭代记账（每轮记录）、阻塞协议（出错怎么说）。

cookbook 里那个 Deep Hedging 复现案例特别说明问题：agent 把 paper 的定价机制、Heston 参考价、CVaR 训练全跑出来了，但**因为原作者没放种子和 checkpoint，最后必须诚实标注”近似复现，非精确神经网络重放”**。这才是 Goal 模型该有的样子 —— 不是装作完成了，是用证据说明完成到哪了。

社区里被反复验证的失败模式：

  • Confident drift：目标含糊 → agent 自己脑补一个解释 → 14 小时跑完发现解决的是错的问题
  • Missing context：项目里有但 agent 读不到的文件 → 假设在长时跑中累积放大
  • Token spend surprise：必须先在 OpenAI 后台设 hard limit
  • Skill 缺失：跑前没装的工具，跑中装不上

Alex Finn 实测得出的反直觉建议：别自己手写 prompt，让另一个 LLM 看你代码库后帮你起 /goal prompt，他原话是 “basically any prompt I hand-write after /goal is never good enough.”

5. 边界判断：哪些活该用 Goal，哪些不该

cookbook 给的清单很坦白：

适合 Goal：性能优化、flaky test 排查、依赖迁移、bug 复现猎杀、多步重构、benchmark 驱动调优、需要最终 artifact 的研究复现。

不适合 Goal：一行编辑、简单解释、短 code review、含糊的”做得更好”、用 Goal 掩盖你自己其实没想清楚要什么。

可以提炼出一个判断式：「这事能不能被一段可执行的脚本/测试验证完成？」

  • 能 → Goal 适合，Codex 会循环到证据满足
  • 不能 → 用普通 prompt，别为浪漫去 burn token

6. 真正的工程拐点是什么

Goal / Ralph Loop 看起来像个”小功能”，但它意味着 coding agent 的角色定义在变：

  • 2024 年的 agent = 副驾驶（Copilot），人是司机
  • 2025 年的 agent = 实时同事（Cursor / Claude Code），人是审查者
  • 2026 年的 agent = 异步工程师（/goal、Background Agents、Threads），人是产品经理 + reviewer

Geoffrey Huntley 那句”我现在是程序员，但我编程的是循环本身”听着像段子，工程上是真的 —— 一旦目标 / 证据 / 预算 / 状态都可以被结构化表达，agent 的工作就从”逐 turn 对话”变成了”预算约束下的搜索过程”。

但要泼一盆冷水：这不是 AGI 也不是 autonomy。OpenAI 自己反复强调它是 user-controlled completion contract。token 成本是 10000 倍量级，confident drift 在长时跑里几乎必然发生，必须把它当成”夜里跑的高风险批处理”来管 —— 上 hard limit、上版本控制、上明确的验证脚本、跑完当 PR 审。

工程师真正该学的不是怎么按 /goal，是 怎么把一个含糊的需求写成一个可被证据闭环的目标。这件事过去叫”写好 spec”，现在变成你能不能让 agent 自动在 spec 上收敛。

7. 给大哥们的实操清单

  1. **升级到 Codex CLI 0.133+**：npm install -g @openai/codex@latest 或 brew upgrade --cask codex
  2. 先在 OpenAI 后台设 spending hard limit，再做夜跑实验
  3. 跑前装好所有需要的 skill / MCP，Goal 跑起来后装不上
  4. **用 meta-prompt 起草 /goal**：让 Claude / GPT 先读你代码库再写 prompt
  5. 完成条件必须可执行验证：测试、benchmark、文件存在性，三选一
  6. 第一次跑 1 小时预算试水，跑完看 token 账单、看 diff、看 evidence ledger
  7. Goal 跑中不要插嘴，破坏 deterministic context；要改就 pause / clear 重来

最后一句：如果你过去一年还在为”agent 老是停下来等我”焦虑，2026 这波更新解决的就是这个问题；但解决的方式不是让 agent 变聪明，而是逼你把”什么叫做完”想清楚。
