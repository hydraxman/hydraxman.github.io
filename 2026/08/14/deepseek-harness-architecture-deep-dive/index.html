DeepSeek Harness 深度拆解：当 Agent Runtime 里“一切皆插件”

如果把 AI Agent 比作一台电脑，模型只是处理器。文件系统、终端、浏览器、会话记录、权限控制和界面，才决定这台“电脑”能不能真正完成工作。

DeepSeek Harness 做了一件很特别的事：它把这些能力全部拆成插件。你可以替换模型，调整工具，换掉存储方式，增加新的界面，甚至让 Agent 临时挂载一段新能力，而不需要重写整个运行循环。

这篇文章不要求你先读源码。读完后，你应该能回答四个问题：

  • DeepSeek Harness 和普通的 Coding Agent 有什么区别？
  • 一个任务在它内部是怎样跑起来的？
  • 你可以怎样使用和扩展它？
  • 当前版本适不适合放进生产环境？

普通用户为什么要关心 Harness

很多 Agent 产品把功能固定在应用里。你可以聊天、运行命令、修改文件，但很难替换底层模型、执行环境或权限策略。团队想接入自己的工具时，往往要绕过原来的架构。

DeepSeek Harness 的思路更接近“组装运行时”。同一个 Agent 核心可以服务四种入口：

  • 在浏览器里作为 Coding Agent 使用；
  • 在命令行里执行一次性任务；
  • 通过 ACP 接入其他 Agent 客户端；
  • 通过 SDK 嵌入自己的自动化系统。

它适合三类人：

  1. 想研究 Agent Runtime，而不满足于只调用一个聊天 API 的开发者；
  2. 需要替换模型、工具、存储或执行环境的团队；
  3. 想开发 Agent 插件、工作流、Subagent 或自定义界面的工程师。

如果你只想找一个开箱即用、接口长期稳定的日常助手，现阶段的 DeepSeek Harness 反而可能太重。它仍处于 Developer Preview，架构能力走在稳定性前面。

它的核心不是一个大类，而是一棵插件树

DeepSeek Harness 的启动过程可以理解为五层装配：

第一层：入口

Web UI、Headless CLI、ACP 和 JSON-RPC SDK 只是不同入口。它们最后都把输入交给同一套 Agent 与 Session 服务。

这意味着 Web 不是另一套后端，ACP 也不是单独实现的 Agent。你从哪个入口进来，底层使用的运行循环和会话日志仍然一致。

第二层：Profile 与 Bundle

Profile 决定这次启动要加载哪些 Bundle。官方自带的 Web profile 可以简化为：

dsh-base 提供 Agent、Session、模型、工具、Skills、Subagent、权限和持久化。dsh-web-app 再加上 HTTP Server、API Gateway 和浏览器插件。

你可以继续叠加自己的 patch。需要注意的是，同一个插件配置被后层覆盖时，替换的是整个 config，不是递归合并。只改一个字段时，也要保留其他仍然需要的字段。

第三层：Cordis 插件内核

Cordis 管理插件树、服务依赖、事件和生命周期。插件可以注册工具、Prompt、监听器或界面组件；卸载插件时，这些注册会自动撤销。

这让 Harness 可以在不复制 AgentLoop 的情况下替换能力。例如 Shell 工具不需要知道命令最终跑在本机、Windows ACL 沙箱，还是 E2B 远程环境。它只调用统一的执行接口。

第四层：Agent 执行脊柱

Agent Registry、AgentLoop、Session、System Prompt、Tool Registry 和 LLM Adapter 组成主执行链。

这里最重要的原则是：模型上下文来自 Session 日志，而不是藏在某个临时数组里。进程重启后，只要 Session 仍在，就能重新推导模型应该看到的消息。

第五层：能力插件

文件系统、Shell、PTY、LSP、Skills、MCP、Subagent、Workflow、Approval、Sandbox 和持久化都位于能力层。团队可以按需要启用或替换。

一个任务怎样变成多个 Step

在 Harness 里，一次用户任务叫一个 Turn。一个 Turn 可以包含多个 Step。

执行过程可以压缩成下面几步：

  1. 用户输入进入 Inbox；
  2. Agent 打开一个 Turn；
  3. 系统组装 Prompt 和可用工具；
  4. Session 推导模型历史；
  5. 模型开始流式输出；
  6. 如果模型调用工具，Harness 执行工具并记录结果；
  7. 工具结果进入下一个 Step；
  8. 没有后续工作时，Turn 结束。

这解释了为什么一个问题可能触发多次模型请求。第一次请求决定读取文件，第二次请求根据文件内容决定修改方案，第三次请求再检查结果。对用户来说是一个任务，对 AgentLoop 来说是同一个 Turn 里的多个 Step。

并行工具也有秩序。可并行的调用会进入有上限的执行池；必须独占的调用会形成屏障。即使工具完成的先后顺序不同，Session 仍按模型原始调用顺序记录结果，避免恢复会话时出现上下文漂移。

Session 日志为什么重要

Harness 会把 Turn、Step、用户消息、模型流式片段、完整回答、工具调用和工具结果写入同一条事件日志。

这条日志同时服务三件事：

  • Web UI 根据它还原对话；
  • AgentLoop 根据它重建下一次模型请求；
  • 持久化层根据它恢复、导出或查询 Session。

模型输出的流式片段不会直接成为最终事实。Harness 会先收集片段，再提交完整的 assistant/message。如果请求重试，未提交的内容不会混进正式对话。

对于长任务，这种设计比单纯保存聊天文本更可靠。工具到底执行过什么、哪个 Step 被取消、模型在什么配置下生成回答，都能从事件中还原。

“一切皆插件”到底能换什么

Harness 把一种能力拆成三个角色：

  • Service Definition 定义统一接口；
  • Service Provider 提供具体实现；
  • Consumer 把能力呈现为 Tool、UI 或 API。

以文件系统为例，模型面对的是文件工具，工具面对的是统一文件接口，Provider 决定文件来自本机还是远程 Sandbox。

这种拆法带来几个实用场景：

  • 把默认模型换成其他 Provider，而不改 AgentLoop；
  • 把 Shell、PTY 和 LSP 一起迁移到远程执行环境；
  • 给特定 Agent 增加一组 Skills，而不影响其他 Session；
  • 通过 MCP 挂载外部工具；
  • 给 Web UI 增加新的设置页或工具结果卡片。

Agent 还能临时扩展自己

Harness 提供一个可选的 cordis Agent Preset。启用后，Agent 会获得五个特殊工具：

  • 检查当前插件和服务；
  • 定义一个临时插件；
  • 运行插件；
  • 停止插件；
  • 删除临时定义。

它可以根据任务临时增加工具、Prompt 或 UI 组件，然后在任务结束后撤回。

这项能力默认不会出现在 Standard 或 Headless profile 中。动态插件只保存在当前进程内，重启后消失，也不会自动写入配置文件。它使用的 node:vm 不是严格安全边界，权限等级应按 Bash 工具对待。

普通用户可以先忽略这项能力。它更适合插件开发者验证想法，而不是在无人值守的生产任务中随意开放。

当前已经覆盖哪些能力

使用场景 Harness 提供的能力
代码与项目操作 文件读写、Shell、PTY、LSP、工作区管理
上下文扩展 Skills、MCP、Agent Instructions、压缩与引用
多 Agent 编排 Subagent、Fork、Workflow、后台 Jobs、Goal
产品接入 Web、Headless、ACP、JSON-RPC SDK
安全控制 Approval、Permission Preset、Sandbox、凭据管理
持久化 JSONL Session、附件、投影缓存、可选 SQLite 查询

这些能力不会在每个入口全部打开。

ACP 目前主要面向自动化，只支持创建新 Session、发送文本、取消任务、接收已提交回答和处理一次性权限请求。它还不支持恢复、删除、Fork Session，也不暴露完整的编辑器、终端、MCP 和计划界面。

MCP 客户端同样不是默认启用项。MCP Server 的启动命令属于宿主可信代码，不受 Agent Sandbox 保护。接入前应像审查本地程序一样审查它。

三个必须知道的安全边界

Sandbox 主要限制写入，不等于完全隔离

默认 workspace-write 会限制文件修改范围，但不会屏蔽所有读取、网络访问和进程可见性。

本地 Sandbox 会按系统选择实现：Linux 使用 bwrap 或 Landlock，macOS 使用 Seatbelt，Windows 使用 ACL restricted token。不同平台的隔离强度并不完全相同。

本地凭据文件挡不住同一用户进程

Harness 会把凭据文件设成用户私有权限，但 Agent 工具与 Harness 运行在同一个系统用户下。文件权限能阻止其他用户，不能阻止同一 UID 的工具主动读取。

高敏感场景应使用独立系统用户、容器、远程凭据代理或系统 Keychain，而不是只依赖本地 YAML 文件。

插件与配置要按代码审查

Cordis 配置支持 JavaScript 表达式，插件可以注册服务、运行命令、访问文件和修改界面。第三方插件、Bundle 与 MCP Server 都属于代码供应链，不是普通提示词。

固定版本、检查生命周期脚本、阅读权限范围，再放进隔离环境验证，是更稳妥的安装方式。

现在该不该用

适合现在开始尝试：

  • 学习 Agent Runtime 的完整架构；
  • 开发工具、Skills、Subagent 或插件；
  • 在本地工作区试验 Coding Agent；
  • 固定版本后嵌入内部原型。

暂时不建议直接承担：

  • 不可丢失的关键生产任务；
  • 无认证的公网服务；
  • 存放高敏感凭据的共享环境；
  • 无人审核的第三方插件生态。

第一次使用时，保持默认本地地址和审批策略，选择一个可丢弃的测试项目，并备份 Session 数据。等你熟悉 profile、权限和持久化以后，再逐步增加 MCP、Subagent 或远程执行环境。

版本说明

DeepSeek Harness 仍是 Developer Preview。本文对应公开仓库 master 的 0.1.0-rc.5 代码；同一时间 npm 的最新包已经是 0.1.0-rc.6，而且暂时没有 Git Tag 或 GitHub Release 可以把两者精确对应起来。

这意味着升级前应先看变更，插件和 Session 格式也不应假定长期兼容。想稳定试用时，固定 npm 版本或 Git commit，比直接追随 latest 更稳妥。
